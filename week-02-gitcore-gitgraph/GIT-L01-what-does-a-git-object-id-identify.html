GitCore · Lesson 01 · Content addressing from first principles

Same bytes, two paths. One stored object.

Before the explanation: make a prediction

Two differently named files contain the same bytes. Predict whether their blob IDs match, whether calculating an ID stores an object, and what would still identify each filename.

Write your reasoning before reading further; this prompt does not grade or save an answer.

Two files in a repository contain exactly the same bytes. Change one character in one of them. How does Git tell the old content from the new without leaning on a filename, a date, or a human-written version label? This lesson derives Git’s object model from that single problem, then follows it all the way to monorepos, CI fleets, mirrors, and supply-chain provenance.

Start with no assumptions.

You need only to know that a file is a sequence of bytes and that Git records versions of a project. Every other term—hash, blob, object database, loose object, packfile, object format—is built up before we depend on it. The goal is not to memorise git hash-object; it is to understand exactly what its output means, and what it does not prove.

Part 1 · Begin with the real-world promise

What would it mean for Git to “know” a version of a file?

You have two files in a source repository: frontend/src/App.jsx and backup/App.jsx. They happen to contain exactly the same bytes. Are these necessarily two different pieces of stored content? Now suppose one file changes by a single character. Git must distinguish the old content from the new, and it must do so without relying on a filename, a modification date, or a label someone typed.

frontend/src/App.jsx backup/App.jsx
The promise

What an engineer expects from version control

“If I ask for the version of this file that was reviewed and released, I get exactly those bytes—not a similar file, not a file with the same name, not whatever is newest.” Every later step in delivery—review, CI, build, deploy, rollback—depends on this.

The engineering question

What must be true?

There must be a name for content that is derived from the content itself, so that the same content always gets the same name and different stored content normally gets a different name, subject to hash-collision limits. The name must be usable to retrieve the content, and something else must remember which path refers to which content.

The central question: How can Git identify stored content independently of the path where a file appears, and how can we inspect that content by its identifier? By the end you should be able to explain content-addressed storage, identify a blob, distinguish calculating an ID from writing an object, and make evidence-based statements about what a hash does and does not guarantee.

Why a filename cannot be the identity

A path such as frontend/src/App.jsx is a name. Names are assigned by people and can be reused: the same path holds different content on different days, and the same content can sit under many paths. A date is no better—two machines’ clocks disagree, and two edits can happen in the same second. A human-written label such as “v2-final” is a promise, not a measurement. What Git needs is a name that is a function of the content: compute it from the bytes, and anyone using the same object format, typed representation and conversion rules gets the same answer.

Build the vocabulary from everyday language

These words appear throughout the lesson. Learn the plain meaning here; the glossary at the end gives fuller definitions.

Byte

The basic unit of stored data: a number from 0 to 255. A file is an ordered sequence of bytes. A space, a newline, and an invisible line-ending character are all bytes and all count.

Hash function

A procedure that turns input of any length into a fixed-length output, called a digest. The same input always gives the same digest; changing a single input bit is designed to change the output unpredictably.

Object

A typed piece of data that Git stores: a blob (file content), a tree (a directory listing), a commit (a snapshot plus history), or an annotated tag.

Object ID

The hash of an object’s typed representation, written as hexadecimal characters. Often called a “SHA” or “hash” informally; Git’s documentation calls it an object name or object ID (OID).

Blob

The object type that holds the bytes of one file’s content—and nothing else. No filename, no directory, no permissions, no timestamp.

Object database

The store inside a repository where Git keeps objects, keyed by object ID. In an ordinary repository it lives under .git/objects.

Working tree

The ordinary files and folders you edit. They are not the repository’s stored history; Git reads them to create objects.

Content-addressed storage

A store where the key used to look something up is computed from the thing itself, instead of being chosen by a person.

Object format

The hash algorithm a repository uses for its object IDs: sha1 (the default) or sha256. It fixes the length and meaning of every ID in that repository.

Part 2 · Derive the mechanism

From file bytes to a stored, findable object in five steps.

Begin with a simple key-value store: key → value. A conventional filesystem lets a person choose the key (the path). A content-addressed store derives the key from the value. Git’s object database is content-addressed: an object ID is derived from the object’s type and content using the repository’s configured hash algorithm. That makes an object retrievable by ID without knowing any working-tree path. Click each step to see what happens and how it can fail.

Step 1 · Input

Git reads the exact file bytes

The input is the file’s byte sequence as Git will store it—after any configured conversion such as line-ending normalisation or a clean filter. Not the filename, not the modification time, not the permissions.

Example: two files that look identical on screen but differ in a trailing newline or CRLF versus LF are different working-tree byte sequences; compare conversion rules and object formats before predicting their stored IDs.

The simplified picture—and the one detail it hides

object bytes + object type + length │ ▼ repository hash algorithm │ ▼ object ID

The drawing is simplified only in its layout: the type and length are not metadata stored beside the hash, they are part of the bytes that are hashed. Git builds a header—the type name, a space, the content length in decimal ASCII digits, and one NUL byte—and hashes header followed by content. It is therefore not simply a hash of the file’s raw bytes. Git’s own hash-function transition document states this directly: the SHA-1 name of an object is the SHA-1 of the concatenation of its type, length, a NUL byte, and the object’s content.

Why include the type?

The four object types are interpreted differently. A tree’s bytes are a binary listing of entries; a commit’s bytes are text headers and a message. If the type were not hashed, the same bytes stored as a blob and as a tree would share an ID, and a reader could not tell from the ID alone how to parse what it retrieved. Hashing the type makes “blob with these bytes” and “tree with these bytes” different objects.

Why include the length?

The header is a framing device. With the length declared up front, a reader knows exactly how many content bytes follow the NUL and can detect truncation. It also means the hashed representation is unambiguous: there is exactly one way to split header from content. git cat-file -s reports this content length, not the size of anything on disk.

Why compress for storage but hash before compressing?

Storage is cheaper when compressed, so Git deflates objects with zlib before writing them. But compression output depends on the compression level and library version. If the ID were a hash of compressed bytes, changing core.looseCompression would rename every object. Hashing the logical, uncompressed representation keeps the ID stable no matter how it is stored.

Why is a path never part of a blob?

Because a path is a fact about where content appears in one snapshot, not about the content. Paths live in tree objects, which map each name and file mode to an object ID. Keeping them out of the blob is what lets one blob be referenced from many paths and many snapshots without being stored again.

Keep this mental picture: an object ID is the output of a deterministic function over type + length + content, computed with the repository’s hash algorithm. Changing a hashed input normally changes the ID; finite hashes do not provide a mathematical no-collision guarantee. Change something that is not an input—the filename, the time, the disk layout, the compression—and the ID stays the same.

Part 3 · The incident and its observations

“The repository is corrupt.” Is it?

A teammate is preparing a release script. They run git hash-object payload.txt in a disposable repository and copy the ID it prints. A minute later, git cat-file -p with that ID fails with “Not a valid object name.” They post in the team channel: “The repo is corrupt, should I run repair tooling?” Another teammate adds that their own script, which validates IDs as exactly 40 characters, just rejected an ID from a newly created repository. Before anyone repairs anything, decode the terms in the story.

git hash-object

A plumbing command that computes the object ID a file’s content would have. By default it only calculates and prints; it does not write.

-w

The option that tells hash-object to actually write the object into the object database. Without it, nothing is stored.

git cat-file

A plumbing command that reads an object by ID. -t prints its type, -s its content size, -p pretty-prints its content, and -e exits with status 0 if the object exists and is valid.

Plumbing

Git’s low-level commands with stable, scriptable output, as opposed to the friendly “porcelain” commands like git status. Plumbing exposes the object model directly.

Loose object

An object stored as its own zlib-compressed file under .git/objects/, named from its ID. New objects usually start loose.

Packfile

A single file that holds many objects, often delta-compressed against each other, with an index for lookup by ID. Maintenance moves loose objects into packs.

Inspect each observation: what does it truly prove?

Open each card. Ask: “What does this establish, and what claim would go beyond it?”

Important reasoning rule: Do not jump from “cat-file cannot find it” to “the repository is corrupt, run repair tooling.” That is a guess about the cause—and some repair actions, like pruning or hand-editing .git/objects, can destroy evidence or data. Part 4 · Four questions, four kinds of evidence

Identity is one question. Three others stay separate.

An object ID is useful for naming and checking Git objects. It is tempting to stretch it into a much larger claim: “the ID matches, so the code is the right code, from the right person, approved, and safe.” Those are four different questions, and each needs its own evidence. Click each one to see what it asks, what evidence answers it, and the false conclusion it tempts people into.

Question 01 · Identity / integrity

Identity / integrity

Does this ID resolve to the object being inspected in this repository, and do the stored bytes still hash to that ID? Git’s object model answers this question well: reading an object by ID and re-hashing it detects accidental corruption, and the ID pins exactly one byte sequence.

Example: Evidence: git cat-file -t/-s/-p <id> and git fsck in this repository. False conclusion to avoid: “The ID resolves, so the change is trustworthy.”
Precision about SHA-1

What “SHA-1 is broken” does and does not mean

A hash function maps an unbounded input space into a finite output space (2160 values for SHA-1, 2256 for SHA-256), so collisions—two inputs with one digest—must exist mathematically. Security depends on nobody being able to find them. In February 2017 researchers from CWI Amsterdam and Google published the first practical SHA-1 collision, “SHAttered”: two different PDF files with the same SHA-1 digest. In 2020 Leurent and Peyrin published a practical chosen-prefix collision (“SHA-1 is a Shambles”), where the attacker can choose two different starting prefixes and still make them collide.

Both are collision attacks: the attacker prepares both colliding inputs. Neither is a second-preimage attack, which would let someone forge new content matching an ID that already exists and that they did not create. So the realistic Git threat is not “someone rewrites history you already have”; it is “someone who controls what you will accept prepares a benign and a malicious object with one ID.”

Precision about Git’s response

Hardened SHA-1 and the SHA-256 object format

Git’s hash-function transition document records that Git v2.13.0 and later moved to a hardened SHA-1 implementation by default, which is not vulnerable to the SHAttered attack. The hardened implementation (“collision detection”) produces ordinary SHA-1 digests for ordinary input, so existing object IDs did not change; it additionally detects input carrying the tell-tale patterns of the known cryptanalytic collision technique and treats it as an error instead of hashing it silently. The same document is explicit that SHA-1 is still weak and it is prudent to move past it.

The long-term answer is the SHA-256 object format: git init --object-format=sha256. The git init manual states that sha1 is the default, that SHA-256 is available where enabled, and that at present there is no interoperability between SHA-256 and SHA-1 repositories. A SHA-256 repository is a different universe of IDs, not a stronger checksum bolted onto the same IDs.

Keep the four questions apart. Git’s object model helps with identity and graph relationships. It does not replace review, CI, signing and provenance policy, or production verification. Later stages of this course connect a commit to tested build artifacts and deployed workloads; the object ID is the first link of that chain, not the whole chain.

Part 5 · Disciplines for working with object IDs

Six habits that keep scripts, pipelines, and people honest about IDs.

A control is a deliberate check or guardrail that keeps work within known boundaries. Each habit below exists because a specific, observed failure is otherwise easy to make. Together they turn “I have a hash” into a claim you can defend.

01

Calculate and write are different acts

Know whether the object exists, not just its name.

First-principles question: Has this object been written to this object database, or have I only computed what its name would be?

git hash-object payload.txt calculates and prints the ID. git hash-object -w payload.txt also writes the object. The git hash-object reference documents this distinction. Calculation does not request object storage, though configured filters can execute processes—useful to ask “what would this content be called?” Writing changes repository state.

  • Use -w only when you intend to store.
  • Verify existence with git cat-file -e <id> (exit status 0 means present and valid).
  • Treat “not found” after calculate-only as expected, not as corruption.
Failure it prevents

Declaring a repository corrupt, or a release “stored,” on the basis of a calculated-only ID.

Evidence/output

The command that was run, with or without -w, and a cat-file -e result.

02

Inspect the logical object, not the disk

Use plumbing; never hand-edit .git/objects.

First-principles question: Am I asking about the object, or about one possible physical place it might be stored?

An object may be loose, packed, in an alternate object store, or (in a partial clone) on a remote that will supply it on demand. A path derived from the ID only finds loose objects. git cat-file answers the logical question wherever the object lives.

  • git cat-file -t / -s / -p <id> for type, size, content.
  • git verify-pack -v <pack>.idx to see what a pack holds.
  • git fsck to check connectivity and validity.
Failure it prevents

Concluding an object is missing because a loose file is absent; corrupting a repository by editing compressed objects.

Evidence/output

Plumbing output that is reproducible on any clone.

03

Detect the object format

Never hard-code “40 characters.”

First-principles question: Which hash algorithm defines IDs in this repository?

SHA-1 IDs are 160 bits, shown as 40 hexadecimal characters. SHA-256 IDs are 256 bits, shown as 64. A script that validates or slices IDs by a fixed length will break on the other format—or, worse, silently truncate.

  • Ask the repository: git rev-parse --show-object-format prints sha1 or sha256.
  • Derive expected length from that answer.
  • Never compare IDs across repositories with different formats; they cannot interoperate.
Failure it prevents

Tooling that rejects valid IDs, or databases with fixed-width columns that truncate them.

Evidence/output

Format recorded alongside every stored ID.

04

Store full IDs; display abbreviations

Short IDs are for humans, and only for now.

First-principles question: Will this short prefix still name exactly one object after the repository grows?

Git accepts a unique prefix of an ID and prints abbreviations (commonly seven or more characters) for readability. Uniqueness is a property of today’s object set. As objects are added, a prefix that was unique can become ambiguous, and Git then refuses to guess. Git’s default abbreviation length is chosen automatically and grows with the repository’s size.

  • Write full IDs into release records, lockfiles, and databases.
  • Resolve a prefix once, with git rev-parse --verify, then keep the full result.
Failure it prevents

Release records or rollback scripts that stop resolving years later.

Evidence/output

Full-length IDs in every durable record.

05

Control the exact bytes

Newlines, encodings, and filters are content.

First-principles question: What bytes will Git actually hash for this path?

Two files that look alike may differ in whitespace, line endings, encoding, or a single byte; they are different byte sequences and normally get different IDs. When a path is given, git hash-object applies the repository’s conversion rules (line-ending normalisation, clean filters from .gitattributes); --no-filters hashes the raw file instead.

  • Use printf, not echo, so newlines are explicit.
  • Check .gitattributes and core.autocrlf when IDs differ across machines.
Failure it prevents

“Same file, different hash” confusion across Windows and Linux, or across shells.

Evidence/output

A byte comparison (cmp, od -c) alongside the IDs.

06

Keep identity separate from trust

An ID names; something else must vouch.

First-principles question: Beyond “these are the bytes,” who says these bytes are acceptable, and how would I check that?

Authenticity needs signatures or attestations; authorization needs review and branch policy; fitness needs tests and production verification. Each produces its own evidence that refers to an ID. The ID makes those statements precise; it does not make them.

  • Record which ID was reviewed, built, and deployed—separately.
  • Prefer IDs over mutable names in every hand-off.
Failure it prevents

Treating a matching hash as approval, authorship, or safety.

Evidence/output

Review, signature, CI, and deploy records, each pinned to a full ID.

Engineering decision record

Inspect through plumbing, not internal files

Decision: inspect Git’s logical objects through plumbing and inspection commands instead of editing internal files directly.

Reason: supported commands express the object model, are easier to reproduce, and avoid coupling the exercise to a physical storage layout.

Trade-off: the output requires interpretation; Git does not print a single friendly “file version” record that contains every relationship.

Revisit when: diagnosing corruption, investigating object packing, or studying Git’s hash-format transition in a dedicated advanced lesson.

Engineering curiosity

Why not store a separate copy for every filename?

A naive version-control design could write a full independent copy of every file at every path and every version. A content-addressed design names content independently and lets tree entries refer to it. When multiple entries have identical blob content, they point to the same logical object. This reduces duplication and makes object identity independent of the current path.

The value is not “every repository is a fixed percentage smaller.” Actual storage depends on file content, change patterns, packing, compression, and history. Delta compression in packfiles is a separate physical optimisation layered under the logical model. Measure a real repository before claiming a storage or performance percentage.

Part 6 · Worked example from first principles

Hash hello by hand, then find it in the database.

Run these only in a disposable repository, such as the one GIT-LAB01 creates. The deterministic blob outputs below were rechecked in a disposable SHA-1 repository; if your repository uses SHA-256, your IDs will differ and be 64 characters long—which is itself part of the lesson.

$ mkdir demo && cd demo && git init --initial-branch=main $ printf 'hello\n' > payload.txt $ git hash-object payload.txt ce013625030ba8dba906f756967f9e9ca394464a

That is a 40-character hexadecimal string: 160 bits, a SHA-1 digest. But a SHA-1 digest of what? To answer from first principles, we need four concepts.

Concept 1

The header is real bytes

The file holds 6 bytes: h e l l o and a newline. Git builds the blob representation as the ASCII text blob, one space, the length 6 in decimal digits, one NUL byte, then the six content bytes. You can hash that yourself: printf 'blob 6\0hello\n' | shasum (use sha1sum on most Linux systems) prints ce013625030ba8dba906f756967f9e9ca394464a—the same ID.

Concept 2

The raw bytes give a different digest

printf 'hello\n' | shasum prints f572d396fae9206628714fb2ce00f72e94f2258f. That is a perfectly good SHA-1 of the file, but it is not the Git object ID. This is the observation that proves the header is hashed. A tool that “verifies” a Git blob by running sha1sum on the checked-out file is checking the wrong thing.

Concept 3

NUL is one byte, not two characters

In blob 6\0, the \0 is notation for the single byte with value zero. It is not the two printable characters backslash and zero. Shell printf interprets \0 as that byte; a text editor would not. The NUL is what separates header from content unambiguously, because the length digits never contain it.

Concept 4

Where a loose object lands

With -w, Git deflates the whole representation (header included) with zlib and writes it to .git/objects/ce/013625030ba8dba906f756967f9e9ca394464a: the first two hex characters become a directory, the remaining 38 the filename. That fan-out keeps any single directory from holding millions of entries. Decompress it read-only and you see blob 6\x00hello\n.

The key deduction: a Git object ID identifies a typed byte sequence in one object format. It is not a hash of the file, of its name, or of its location on disk. Any reasoning that ignores the header, the type, the exact bytes, or the format will predict the wrong ID.

Follow the experiment step by step

Calculate without writing

git hash-object payload.txt prints ce0136…464a. Now git cat-file -e ce013625030ba8dba906f756967f9e9ca394464a; echo $? prints a non-zero status: the object does not exist yet. Nothing is wrong; nothing was written.

Reproduce the ID by hand

printf 'blob 6\0hello\n' | shasum gives the same digest. printf 'hello\n' | shasum does not. You have now verified the header rule yourself, rather than trusting a diagram.

Write the object

git hash-object -w payload.txt prints the same ID and creates .git/objects/ce/013625…. Writing again is a no-op: the name is a function of the content, so the object is already there. Writes of identical content are naturally idempotent.

Inspect by ID only

git cat-file -t ce0136… prints blob; -s prints 6; -p prints hello. No path was needed. Replace <object-id> placeholders in any instructions with a value Git actually printed—angle brackets are not typed literally.

Show path independence

Copy the file to backup/App.jsx and frontend/src/App.jsx (same bytes), stage and commit. git ls-tree -r HEAD lists both paths with the same blob ID. One logical blob, two tree entries.

Pack, then look again

Run git gc. git count-objects -v can show reachable objects moved into packs; counts depend on reachability, age and configuration. The loose file may be gone—yet git cat-file -p ce0136… still prints hello. git verify-pack -v .git/objects/pack/*.idx lists the blob with its type, size, size in pack, and offset.

Change the format, change the ID

In a new repository created with git init --object-format=sha256, printf 'hello\n' | git hash-object --stdin prints the 64-character 2cf8d83d9ee29543b34a87727421fdecb7e3f3a183d337639025de576db9ebb4. Same bytes, same header rule, different algorithm, different—and non-interoperable—ID.

Part 7 · From symptom to diagnosis

“Object not found” has at least six different causes.

A diagnosis is an explanation supported by observations after alternatives have been ruled out. When Git cannot find or read an object, the tempting move is a repair command. But Git’s objects are content-addressed, which gives you an unusual advantage: any other clone that has the object has exactly the same bytes under exactly the same ID. Recovery is rarely about reconstructing data; it is about finding out why this database does not have it.

Intervention

An intervention changes repository state: git gc, git prune, re-cloning, deleting a “broken” file under .git/objects, or running hash-object -w. Some interventions are irreversible—pruning removes unreachable objects for good—and they can erase the evidence that would have explained the fault.

Observation

These checks inspect rather than deliberately repair; in a partial clone some can trigger a lazy fetch: git cat-file -e, git rev-parse --show-object-format, git rev-parse --is-shallow-repository, git count-objects -v, git fsck. Choose the next observation by asking which explanation it would rule in or out.

1. Describe the symptom exactly

Record the command, the full ID, the repository path, the Git version, and the exact error text. “Git is broken” cannot be compared against evidence; “cat-file -p ce0136… in ~/demo says Not a valid object name” can.

2. Rule out the trivial explanations first

Are you in the repository you think you are (git rev-parse --git-dir)? Is the ID complete and correctly copied? Does its length match the object format reported by git rev-parse --show-object-format? A SHA-1 ID will never resolve in a SHA-256 repository.

3. Ask whether the object should exist here

Was it ever written—or only calculated without -w? Was it fetched? Is it reachable from any ref? Unreachable loose objects become eligible for pruning once they are older than gc.pruneExpire (two weeks by default), so an object that existed last month may legitimately be gone.

4. Check the clone’s shape

A shallow clone (git rev-parse --is-shallow-repository prints true) deliberately lacks history beyond its boundary. A partial clone made with --filter deliberately omits some objects and fetches them on demand from its promisor remote. In both cases “missing locally” is by design; the question becomes whether the remote can supply it.

5. Only then check integrity

Run git fsck --full to find objects whose bytes no longer hash to their ID, or links to objects that are absent. Before repair, preserve a complete repository backup; linked worktrees, alternates and partial clones may keep required data outside the local .git path. Never hand-edit compressed objects.

6. Recover by ID from another copy

Because names are derived from content, any healthy clone, mirror, or backup that contains the ID has the identical object. Fetching from it restores the exact bytes; there is nothing to “merge.” Afterward, re-run cat-file -e and fsck and record what was missing and why.

Evidence-first is not “never act.” It means gather enough information to choose a safe next action. If a production pipeline is blocked, a pre-approved action such as re-cloning from a known-good remote may be right—record the failing ID and the clone’s shape first, so the cause is not lost.

Part 8 · The operating contract

Eight questions before you trust an object ID in a record.

The object’s responsibility is narrow: preserve a typed piece of content under an object ID. It is not responsible for recording the file’s path, which commit used it, who approved it, or whether an application can run. Trees, commits, references, and higher-level controls answer those questions; GIT-L02 derives their roles. When a release record says “deployed commit abc123…,” an engineer should be able to resolve the commit, inspect the tree it names, relate it to the built artifact, and verify the deployed image. A hash printed on its own does not prove that every downstream step used that same source.

Working-tree file bytes │ │ git hash-object ▼ Candidate object ID │ ├── without -w ──► ID calculated; object need not be stored │ └── with -w ─────► object written to object database │ ▼ git cat-file <ID> inspect type / size / content
01 · Which object format produced this ID?

A SHA-1 ID and a SHA-256 ID for the same bytes are different strings, and the two formats do not interoperate. An ID without its format is ambiguous in principle and unusable across repository types.

Evidence: git rev-parse --show-object-format output recorded with the ID.
02 · Is it a full ID, from which repository?

An abbreviation is unique only within one object set at one moment. A full ID avoids abbreviation ambiguity within its format, subject to collision and integrity assumptions—but it still only resolves in a database that contains the object.

Evidence: full-length ID plus the repository or remote URL it came from.
03 · Was the object actually written and present here?

Calculating a name is not storing a thing. In shallow and partial clones, some objects are intentionally absent locally.

Evidence: git cat-file -e <id> exit status in the repository that will use it.
04 · Which exact bytes were hashed?

Line-ending normalisation, clean filters, and the difference between echo and printf all change bytes. Different IDs require checking the object format, type and converted bytes, not assuming only a file-content difference.

Evidence: byte comparison and the attributes/filters in effect (.gitattributes, core.autocrlf).
05 · Which mutable name was resolved to this ID, and when?

Branches and tags are names that can move. If a pipeline starts from main, the useful fact is which ID main meant at that moment; every later stage should use the ID, not re-resolve the name.

Evidence: “main → full ID at timestamp T,” recorded once at the start of the pipeline.
06 · What vouches for this content?

Identity does not establish authorship or approval. A signature, a provenance attestation, or a review record supplies that—and each should name the full ID it covers.

Evidence: a verified signature or attestation, and the review record, each pinned to the ID.
07 · What was tested and deployed at this ID?

CI builds and tests code checked out at a specific revision. The image or package it produced has its own digest. The deployment runs some digest. Each link must be recorded, or the chain has a gap.

Evidence: CI run → source commit ID → artifact digest → digest observed running in production.
08 · If the object goes missing, where else does it exist?

Content addressing makes every complete copy interchangeable. Recovery depends on knowing which mirrors, backups, or clones hold the full object set, and that they are not themselves shallow or filtered.

Evidence: a named, complete replica and a tested restore that ends with a clean git fsck.

Part 9 · At production scale

One laptop hashes a file. A fleet depends on every ID meaning exactly one thing.

So far we hashed one six-byte file in one repository. Real organisations run monorepos with millions of objects, hundreds of CI runners cloning on every merge, read mirrors in several regions, and release pipelines that hand a version from team to team. Content addressing is the reason most of that works: an ID is a pure function of content, so the object behind it can never change. That single property makes objects useful for verified object caching and deduplication; retention, access control and replica coordination are still required, and pin in provenance records. Each card below is a failure that appears when that property is ignored, stretched, or depended on without noticing.

Failure mode · Stale caches and mutable names

Two jobs “built main” and built different code

Mechanism: A verified immutable object can be cached under its full ID and object format, but damaged data, weak hashes, authorization changes and eviction remain concerns. A build cache needs the complete inputs, including toolchain, dependencies and configuration; the source commit alone is not a sufficient key. Branches, tags, and image tags such as latest are the opposite—mutable names that point at an ID until someone moves them. A cache or a pipeline stage keyed by a name is stale the instant the name moves. If each stage of a pipeline re-resolves main, a merge that lands mid-pipeline means the test stage and the build stage saw different commits.

What operators see: a release whose tests passed but whose artifact behaves differently; a rollback “to v1.4” that deploys something nobody tested because the tag was deleted and re-pushed; two runners reporting the same branch name with different results.

Production control: resolve a name to a full ID exactly once, at the start, and log the resolution. Pass the ID—never the name—to every later stage. Key build caches by all relevant inputs and dependency caches by verified content identity, not just a source ID. Protect release tags from being moved, and treat any name→ID change as an auditable event.

Failure mode · Replica lag and eventual consistency

The webhook arrived before the mirror caught up

Mechanism: Large teams serve fetches from read mirrors close to CI runners to protect the primary. Replication copies refs and objects asynchronously, so a mirror is briefly behind. A push to the primary fires a webhook; a runner immediately fetches from a mirror that has not replicated yet. If the job asks for the branch, the mirror answers with its older ID, and the job silently builds the previous commit while reporting status against the new one. If the job asks for the exact ID, the mirror either has it—in which case verify the returned identity and bytes against the requested object format—or it fails loudly.

What operators see: intermittent fetch or checkout failures that mention a missing ref or object, clustered right after pushes and on particular mirrors; or, worse, no error at all and a build of the wrong commit.

Production control: fetch an advertised containing ref and verify the expected ID, or fetch the ID directly only if server policy permits it; retry with bounded backoff and jitter, and fall back to the primary after a bounded wait. Measure replica freshness directly by comparing ref→ID maps from git ls-remote against primary and mirror. Content addressing makes that consistency check cheap: equal IDs mean equal content, so you compare names, not bytes.

Failure mode · Thundering herd of CI clones

One merge, four hundred simultaneous clones

Mechanism: A full clone transfers the required reachable objects; servers may reuse existing packs, bitmaps and deltas rather than walk and recompress every object for every request. That costs CPU, memory, and egress roughly in proportion to repository history. A merge to a monorepo’s main branch can trigger hundreds of jobs that all clone within seconds; timeouts trigger retries, and retries add load at the worst moment. The repository did not change size—demand did, all at once.

What operators see: Git server CPU and network saturation aligned with merges, clone latency rising from seconds to minutes, queued jobs, and a retry storm that keeps the server saturated after the original burst.

Production control: shrink each request and reuse objects. For throwaway single-build checkouts, a shallow clone (--depth 1; actions/checkout defaults to a fetch depth of 1) transfers only the tip snapshot. GitHub’s guidance recommends blobless clones (--filter=blob:none) for environments that span multiple builds, because later fetches into shallow clones are expensive for the server. Persist object stores on runners, seed from --reference repositories or --bundle-uri bundles, place mirrors near runners, and add jitter to retries. Verify object integrity, format and access policy; object immutability does not make arbitrary build caches correct or guarantee retention.

Failure mode · Pack and garbage-collection cost

Maintenance competes with the traffic it exists to serve

Mechanism: Each distinct stored representation can add an object; unchanged content is reused by ID. Loose objects are one file each, so millions of them strain filesystems; git gc --auto packs them when roughly 6,700 accumulate (gc.auto) or when there are more than 50 packs (gc.autoPackLimit). Repacking searches for good delta bases (by default a window of 10 candidates and a maximum delta chain depth of 50), which is CPU- and memory-heavy and grows with object count. During a repack the old and new packs coexist on disk. Pruning removes unreachable loose objects older than two weeks by default; the git gc manual warns that --prune=now risks corruption if another process is writing concurrently.

What operators see: periodic latency and disk spikes on Git servers; “Auto packing the repository” pauses on developer machines; fetches slowing as pack counts climb; and, after an aggressive prune during a push, objects referenced by a ref but missing from disk.

Production control: schedule maintenance instead of letting it trigger in the request path: git maintenance runs tasks such as commit-graph, loose-objects, and incremental-repack on a schedule; a multi-pack-index lets Git look up objects across many packs without a full repack. Never use --prune=now on a live server. Track loose-object count, pack count, and repack duration as first-class metrics.

Failure mode · Hidden data-plane dependency in partial clones

The repository you “already have” needs the network

Mechanism: A partial clone records its origin as a promisor remote and omits objects matching its filter. When a command needs a missing object—checkout of an old commit, blame, log -p, a diff across history—Git fetches it on demand. Local-looking work becomes remote calls. With a treeless clone (--filter=tree:0), GitHub’s guidance notes that a file-history query such as git log -- <path> can start downloading root trees for almost every commit. A shallow clone has a related trap: history beyond the boundary is simply absent.

What operators see: build steps that hang or fail only in network-restricted stages; a Git-server outage that breaks pipelines which had “already cloned”; a quiet developer command that turns into thousands of object requests against the server.

Production control: choose the filter per workload, not per organisation: blobless for long-lived checkouts, shallow or treeless only for throwaway builds. Prefetch whatever a job needs before it enters an isolated stage. Treat the promisor remote as a runtime dependency with its own availability target, and watch lazy-fetch volume on the server.

Failure mode · Supply-chain trust in names versus digests

A valid-looking name, the wrong bytes

Mechanism: Whoever can push can move a name: tags can be deleted and re-created, branches force-pushed, image tags overwritten. A digest cannot move. GitHub’s security guidance recommends pinning third-party actions to a full-length commit SHA, noting that an attacker would then need to generate a SHA-1 collision for a valid Git object payload. Container images work the same way: an OCI descriptor names content by a sha256: digest, and image@sha256:… pins exactly those bytes. SLSA provenance links an artifact’s digest to the source revision it was built from. The pin is only as strong as the hash: SHA-1 collision attacks require the attacker to prepare both versions, which matches a malicious or compromised maintainer of something you depend on. Hardened SHA-1 defeats the known attack; SHA-256 repositories are the structural fix but cannot interoperate with SHA-1 repositories, so hosts, mirrors, and tools across a fleet must agree on the format.

What operators see: usually nothing—that is the danger. The substituted artifact runs under a familiar name, passes name-based policy, and appears in logs as the expected version.

Production control: pin every hand-off by full ID or digest; verify signatures or attestations that name that digest; reject deployments of tags without digests at admission; and record the object format with every stored ID so a later move to SHA-256 does not silently break comparisons.

Failure mode · Abbreviation and format skew in tooling

A rollback script that worked for three years

Mechanism: Humans copy short IDs, and tools often store them. A prefix is unique only relative to the current object set; Git chooses its default abbreviation length from the repository’s size precisely because growth creates collisions among prefixes. Separately, databases and validators built around 40-character IDs reject or truncate 64-character SHA-256 IDs. Both are version-skew bugs between an assumption baked into tooling and the repository it serves.

What operators see: an “ambiguous” error from Git when a second object acquires the same short prefix—often discovered during an incident, when a rollback is needed most—or a pipeline that fails on the first SHA-256 repository.

Production control: store full IDs plus object format in every durable record; resolve abbreviations once with git rev-parse --verify; size schema columns for 64 hex characters; test tooling against a SHA-256 repository before one appears in production.

Failure mode · Silent corruption and replica divergence

A disk flips a bit on one replica

Mechanism: Storage fails quietly. If one replica’s copy of an object is damaged, its bytes no longer hash to their ID. Because the ID is a checksum of the content, a reader that re-hashes detects the damage instead of serving wrong code. That only helps if something actually reads and verifies: git fsck checks object validity and connectivity, and transfer.fsckObjects (off by default) makes fetch and receive verify incoming objects.

What operators see: errors on one replica only, often for objects that are rarely read, surfacing months after the fault—sometimes only when a backup is restored.

Production control: schedule git fsck on servers and backups; enable object checking on receive where the cost is acceptable; and repair by fetching the damaged ID from a healthy replica—content addressing guarantees the replacement is byte-identical.

Content addressing turns silent staleness into loud absence—but only if you ask by ID. A mirror, cache, or registry asked for a name can return an old or substituted answer that looks perfectly valid. Asked for an ID, it can only return the exact bytes or fail. Every hand-off that still uses a mutable name is a place where the guarantee quietly stops.

Part 10 · Practice the reasoning

Don’t memorise the slogan. Make the next decision.

Choose an answer before opening the explanation. Each scenario is built from a real misconception; the distractors are things competent engineers do say. Reason from the mechanism: what bytes were hashed, with which algorithm, and what was actually written where.

Scenario 1 · The “corrupt” repository

You ran git hash-object payload.txt and it printed an ID. A minute later, git cat-file -p with that ID reports the object cannot be found. What is the best conclusion?

Reasoning: Without -w, hash-object only calculates and prints. The command did not write an object; in a fresh repository with no prior copy, lookup fails as predicted. A wrong algorithm would give a wrong ID but would not explain a lookup failure for an object that was never written; and packing never hides objects from cat-file, which reads loose and packed objects alike. Repair tooling here risks destroying evidence for no reason.

Scenario 2 · The 64-character ID

A deployment script validates commit IDs with a regular expression requiring exactly 40 hexadecimal characters. It rejects a 64-character ID from a repository another team created last week. What should you do first?

Reasoning: A 64-character ID is what a SHA-256 repository produces. It is not a SHA-1 ID with extra characters—truncating it yields a string that names nothing. Maintenance never changes IDs, because IDs are computed from content, not from storage. Check the format, then fix the assumption baked into the script.

Scenario 3 · Same file, two hashes

A file “looks identical” on a Windows laptop and a Linux CI runner, but git hash-object --no-filters on the working-tree file gives different IDs on each machine. Which explanation is most likely?

Reasoning: Hash functions are deterministic, and neither the filename nor the storage layout is an input to a blob ID. First confirm the same object format and type; then compare the bytes after applicable conversion. Line endings are the classic invisible difference; compare with cmp or od -c, then check .gitattributes and core.autocrlf. Without --no-filters, Git would apply the repository’s conversion rules before hashing, which is often why committed blobs match even when working-tree files do not.

Scenario 4 · The checksum that “fails”

A security reviewer runs sha1sum App.jsx on a checked-out file and reports that the digest does not match the blob ID shown by git ls-tree. They suspect tampering. What do you tell them?

Reasoning: Git hashes a typed representation that begins with a header. sha1sum of the raw file is a correct SHA-1 of a different input, so it will not match. The reviewer’s instinct to verify is good; the check must hash the same thing Git hashes. Paths are not in blobs, and a SHA-1 repository uses SHA-1.

Scenario 5 · The mirror and the webhook

A push to main triggers CI. The runner fetches main from a regional read mirror and builds. Occasionally the build artifact turns out to be from the previous commit, while the status is posted on the new one. What is the most robust fix?

Reasoning: The fault is asking a lagging replica for a mutable name. Asking for an ID makes the result either exactly right or a loud failure, which a retry can handle. Sleeps only make the race rarer; removing mirrors moves the load problem to the primary (clone storms); a shallow clone still fetches whatever the mirror’s main currently is.

Scenario 6 · Where did the loose object go?

After git gc, the file .git/objects/ce/013625030ba8dba906f756967f9e9ca394464a no longer exists. A colleague says the blob was deleted. What observation settles it?

Reasoning: Garbage collection moves reachable loose objects into a packfile. The logical question—does the object exist?—is answered by cat-file -e, which searches loose and packed storage. Hand-copying files into .git/objects and aggressive pruning are interventions that can create the very corruption you feared.

Reason through these, then open each to check

Answer in your own words first. Use the explanations as feedback after committing to a prediction; keep the final transfer response your own.

Q1 · Two files contain identical bytes but different names. Which object type records the names, and what do you expect from their blob IDs?

Tree objects record the names and paths. Expect the same blob ID for both: a blob carries no path, and the bytes and object format are the same.

Check: hash both paths, then git ls-tree -r HEAD after committing.
Q2 · Why does git hash-object payload.txt not prove the object can be retrieved?

Without -w it only calculates and prints the ID; the object need not be written. A failed cat-file for such an ID is the expected difference between calculated and written—not corruption.

Check: git cat-file -e <id> before and after hash-object -w.
Q3 · If one file changes only its trailing newline, what do you test, and what does a changed blob ID tell you?

Calculate the ID before and after, using printf so the newline is explicit. A changed ID tells you the stored byte sequence differs—whitespace and line endings are content. It does not tell you which byte or whether it matters.

Check: printf 'x\n' versus printf 'x' piped to git hash-object --stdin.
Q4 · What can git cat-file -p <id> establish? What does it not establish about a production release?

It shows the content of the object that ID resolves to in this repository. It does not establish author identity, review approval, test coverage, or production health.

Check: separate signature, review, CI, and deployment records, each pinned to the ID.
Q5 · Why should scripts use git rev-parse --show-object-format instead of assuming 40 characters?

SHA-1 is the default, but repositories can use SHA-256, whose IDs are 64 hexadecimal characters. Inspect the format instead of hard-coding it.

Check: run it in a repository created with git init --object-format=sha256.
Q6 · Why inspect objects with cat-file instead of editing .git/objects directly?

Supported commands express the logical object model, are reproducible, and avoid coupling to a physical layout that changes as Git packs objects. The trade-off: the output needs interpretation.

Check: after git gc, the loose path is gone but cat-file still works.

Read every mechanism step without scripting

Git reads the exact file bytes

The input is the file’s byte sequence as Git will store it—after any configured conversion such as line-ending normalisation or a clean filter. Not the filename, not the modification time, not the permissions.

two files that look identical on screen but differ in a trailing newline or CRLF versus LF are different working-tree byte sequences; compare conversion rules and object formats before predicting their stored IDs.

Git prepends the type and the length

Git builds a header: the object type (blob, tree, commit, or tag), one space, the content length in decimal ASCII digits, and a single NUL byte. The bytes that get hashed are header followed by content. This is why the same bytes stored as a blob and as some other type would not share an ID.

for a file containing hello and a newline (6 bytes), the hashed input is “blob 6”, one NUL byte, then those 6 bytes. Hashing that exact sequence with a plain SHA-1 tool reproduces the ID Git prints: ce013625030ba8dba906f756967f9e9ca394464a.

The repository’s hash function produces the ID

Every repository has one object format, fixed when it is created. The default is SHA-1, giving 40 hexadecimal characters. A repository created with git init --object-format=sha256 uses SHA-256, giving 64. Git’s SHA-1 implementation also detects the known collision-attack pattern and refuses such input, which is why it is described as hardened SHA-1.

the same hello file is ce01362… in a SHA-1 repository and 2cf8d83… (64 characters) in a SHA-256 repository. An ID is only meaningful together with the algorithm and repository it came from.

Only -w writes the object into the database

git hash-object without -w only calculates and prints the ID. With -w, Git zlib-compresses header plus content and stores it as a loose object at .git/objects/, using the first two hex characters as a directory name and the rest as the filename. Calculating an ID and storing an object are separate events.

after git hash-object -w payload.txt in a fresh SHA-1 repository, the file .git/objects/ce/013625030ba8dba906f756967f9e9ca394464a exists. Without -w, it does not, and cat-file will not find the ID.

Look up by ID, wherever the bytes live

git cat-file -t, -s, and -p report an object’s type, size, and content from its ID alone. Maintenance such as git gc moves loose objects into packfiles: a .pack file holding many objects, often delta-compressed against similar ones, plus a .idx index for lookup. The storage changes; the ID does not, because the ID names the content, not its location.

after git gc, the loose file under .git/objects/ce/ may disappear, yet git cat-file -t ce01362… still prints blob. If an object is unreachable from any ref, later maintenance may delete it entirely.

Read every evidence category without scripting

Identity / integrity

Does this ID resolve to the object being inspected in this repository, and do the stored bytes still hash to that ID? Git’s object model answers this question well: reading an object by ID and re-hashing it detects accidental corruption, and the ID pins exactly one byte sequence.

Evidence: git cat-file -t/-s/-p <id> and git fsck in this repository. False conclusion to avoid: “The ID resolves, so the change is trustworthy.”

Authenticity

Who vouched for this object? An ID says nothing about who created the bytes. The author and committer fields in a commit are text the creator typed; anyone can write any name. Authenticity needs a cryptographic signature over a commit or tag (OpenPGP, SSH, or X.509) and a trust decision about the signing key.

Evidence: git verify-commit or git verify-tag against keys you trust, or the hosting platform’s verified-signature record. False conclusion to avoid: “The commit says it was written by our lead engineer, so it was.”

Authorization

Was this change permitted to enter the branch it is on? That is a policy question answered outside the object model: branch protection, required reviews, and who may push. A perfectly valid, signed object can still have arrived without the review your process requires.

Evidence: the pull request approval record and the branch rules that applied when it merged. False conclusion to avoid: “It is signed, so it was approved.”

Fitness

Does the code at this ID behave the way we need, in the environment we care about? Only tests and operational checks against this exact version can begin to answer that. Identity, authenticity, and authorization are all necessary context; none of them says the change works.

Evidence: test and check results recorded against this exact commit ID, then runtime signals after deployment. False conclusion to avoid: “It was reviewed and signed, so it works in production.”

Reference · Plain-English glossary

Technical words, without the assumed knowledge.

Use this section whenever a word feels like jargon. Search by a term or a phrase. You do not need to memorise the glossary; learn to ask what each word means in the current situation.

36 terms
Abbreviated object ID

A leading prefix of a full ID, accepted by Git if it is unique in the current repository. Uniqueness can be lost as objects are added, so durable records should store full IDs.

Alternates

A Git mechanism that lets one repository read objects from another repository’s object store. git clone --reference uses it to avoid downloading objects that already exist locally.

Blob

The object type that stores one file’s content—bytes only. It contains no filename, path, mode, or timestamp.

Bundle

A single file containing Git objects and refs that can be transported outside the normal protocol. git clone --bundle-uri can seed a clone from a bundle before contacting the origin.

git cat-file

A plumbing command that reads an object by ID: -t type, -s size, -p pretty-printed content, -e exit status for existence. It reads loose and packed objects alike.

Collision

Two different inputs that produce the same hash digest. Collisions must exist for any fixed-length hash; security depends on nobody being able to find them deliberately.

Hardened SHA-1 (collision detection)

The SHA-1 implementation Git uses by default since v2.13.0. It gives normal SHA-1 results for normal input and detects input crafted with the known collision attack technique, so Git is not vulnerable to the SHAttered attack.

Commit

An object that records a project snapshot (by naming a tree), its parent commits, author, committer, and message. GIT-L02 builds it from the ground up.

Content-addressed storage

A store where each item’s key is computed from its content. The same content always has the same key, and content under a key never changes.

Delta

A compact representation of one object as differences from another “base” object inside a packfile. It is a storage optimisation; the object’s ID is still the hash of its full logical content.

Digest

The output of a hash function. In artifact systems such as OCI registries, a digest like sha256:… names the exact bytes of an image manifest or layer, unlike a mutable tag.

git fsck

A command that verifies objects hash to their IDs, are well-formed, and that references between objects resolve. It detects corruption and missing objects.

Garbage collection (git gc)

Housekeeping that packs loose objects, consolidates packs, and prunes unreachable objects older than a grace period (two weeks by default). git maintenance schedules finer-grained tasks.

Hash function

A deterministic function that maps input of any length to a fixed-length digest, designed so that different inputs practically never share a digest and small input changes alter the whole output.

git hash-object

A plumbing command that computes the object ID for content. By default it only calculates; with -w it also writes the object to the database.

Object header

The bytes <type> <size> followed by a NUL byte, prepended to an object’s content before hashing and storing. It is why a blob ID differs from a plain hash of the file.

Loose object

An object stored as its own zlib-compressed file at .git/objects/<first 2 hex>/<remaining hex>. New objects usually start loose.

Mirror / replica

A copy of a repository kept in sync with a primary, often to serve fetches closer to users or CI. Replication is usually asynchronous, so a mirror can briefly lag.

Multi-pack-index

An index that lets Git find objects across many packfiles at once, reducing the need for expensive full repacks in large repositories.

NUL byte

The byte with value zero, written \0 in notation. In the object header it separates the size from the content. It is one byte, not the characters backslash and zero.

Object database

The repository’s store of objects keyed by ID, commonly under .git/objects, containing loose objects and packfiles.

Object format

The hash algorithm a repository uses for IDs: sha1 (default) or sha256. Shown by git rev-parse --show-object-format. Repositories of different formats do not interoperate.

Object ID

The hexadecimal hash of an object’s header plus content, in the repository’s object format: 40 characters for SHA-1, 64 for SHA-256.

Packfile and index

A .pack file stores many objects, compressed and often delta-encoded; its .idx maps object IDs to positions in the pack for fast lookup.

Partial clone

A clone made with --filter that omits some objects (for example all blobs) and fetches them on demand. Blobless is --filter=blob:none; treeless is --filter=tree:0.

Plumbing and porcelain

Plumbing commands are low-level with stable, scriptable output (hash-object, cat-file). Porcelain commands are user-friendly (status, log).

Promisor remote

The remote a partial clone trusts to supply missing objects later. Commands needing an absent object fetch it from there, which makes the remote a runtime dependency.

Provenance

A verifiable record of how an artifact was produced—for example which source revision and build process—identified by the artifact’s digest.

Reference (ref)

A human-readable name, such as a branch or tag, that points to an object ID. Refs can move; IDs cannot.

Second-preimage attack

Finding a new input that matches the digest of an existing, given input. It is much harder than finding a collision and is not known to be practical for SHA-1.

SHA-1

A hash function with 160-bit output (40 hex characters). Git’s default object format. Practical collisions were published in 2017 and 2020.

SHA-256

A hash function with 256-bit output (64 hex characters). Available in Git as an alternative object format via git init --object-format=sha256.

Shallow clone

A clone made with --depth that truncates history at a boundary. Fast for throwaway builds; later fetches into it can be expensive for the server.

Tree

An object that lists directory entries: each has a mode, a name, and the ID of a blob or another tree. Trees are where paths live.

Working tree

The ordinary editable files of a checkout. Git reads them to create objects; they are not themselves the stored history.

zlib

A widely used compression format (RFC 1950) based on DEFLATE. Git compresses stored objects with it; the object ID is computed before compression, so compression settings never change IDs.
