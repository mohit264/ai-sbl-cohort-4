GitCore · Lesson 02 · Objects, the index, and names

“The version that passed the test.” Which object is that?

Before the explanation: make a prediction

You edit README.md after staging it, then commit without staging again. Predict which content the commit records and whether a branch name by itself proves which version a test used.

Write your reasoning before reading further; this prompt does not grade or save an answer.

A repository holds a React frontend and a FastAPI backend. A teammate asks you to inspect the version that passed the test. You can see the files in your working directory, but that directory might contain uncommitted changes. A branch name such as main is convenient, but the branch can move. This lesson builds, from the objects introduced in GIT-L01, the exact chain Git uses to turn file content into a recorded snapshot and give that snapshot a human-friendly name.

The central question.

How does Git connect file content into a project snapshot, record a commit, and let names such as main and HEAD resolve to that commit? Learn the relationships so that command output becomes evidence, not a collection of vocabulary words. You need GIT-L01 (blobs and object IDs) and the Week 1 habit of evidence-first operation. Nothing else is assumed.

01 · Assemble a version

Follow content from the working tree, through the index, into trees and a commit object.

02 · Name a version

Separate immutable object IDs from movable names: branches, tags, HEAD, and “latest.”

03 · Prove a version

Tie a release to the exact commit that built it, and know what a signature or tag does and does not prove at scale.

Familiar example

Think of a dispatch manifest

Use this comparison to separate the roles, then return to the exact Git mechanism and its limits.

  • Editable goods and notes map to the working tree.
  • A proposed packing list maps to the index.
  • A frozen nested contents manifest maps to trees referencing blobs.
  • A dispatch record with earlier-record links maps to a commit and its parents.
  • A movable “current shipment” label maps to a branch; the desk note selecting that label maps to attached HEAD.

Where the comparison stops helping

A Git snapshot is not a physical copy of every file; unchanged objects are shared. Client timestamps are not a trusted clock, signatures are not approval, and the analogy does not explain merge rules or sparse indexes.

Use only the fresh disposable repositories and Git-context preflight described in the labs. Ordinary full-index, standard untracked visibility and no custom filter assumptions apply to the simple status examples; skip-worktree/assume-unchanged flags and external build inputs need separate checks. The core route is the mechanism, worked example and lab handoff. Fleet-scale sections are optional extension reading, not extra required lab operations or measured time.

Part 1 · Begin with the real-world promise

“Inspect the version that passed the test” must point at exactly one thing.

When a teammate says “the version that passed,” they are making a promise: there is one specific, reproducible set of files, and if you look at it you will see exactly what the test saw. Your job is to turn that sentence into an identifier that cannot drift. The files on your disk cannot be that identifier, because they change every time you type. A branch name cannot be it either, because a branch exists precisely so that it can move.

The promise

What the teammate expects

“If you look at the version I am talking about, you will see byte for byte the same source the test ran against, and so will anyone else who looks next week.”

The engineering question

What must be true?

Every file’s content must be fixed. Every file’s path and mode must be fixed. The whole set must be captured at once, not file by file. And the name we hand to other people must resolve to that captured set every time it is resolved, on every machine, by every team.

First principle: A version is not “the files I have.” A version is a recorded, content-addressed snapshot plus its ancestry. A name for a version is only as trustworthy as the rules that stop that name from being moved.

Start with what you can observe

In a repository with at least one commit, run these six commands from the repository root. Do not simply read the command names and guess. For each output, record what is an object ID, what is a symbolic name, and what relationships connect them.

Build the vocabulary from what you just ran

Every output above falls into one of a small number of categories. Learn the categories first; the rest of the lesson explains how each one works inside.

Working tree

The files currently checked out on disk, which you can edit. Git does not record anything just because a file here changed.

Index (staging area)

A single file in .git that lists, path by path, exactly which content will go into the next commit. git add updates it.

Blob

From GIT-L01: an object holding one file’s content bytes, addressed by an ID computed from those bytes. It has no filename.

Tree

An object that lists names, modes, and object IDs: the directory structure that blobs lack. Trees can contain other trees.

Commit

An object naming one top-level tree, zero or more parent commits, an author, a committer, timestamps, and a message.

Reference and HEAD

A reference (ref) is a name, such as refs/heads/main, that resolves to an object ID and can be moved. HEAD names your current checkout context.

Part 2 · Derive the mechanism

From file content to a named version, one relationship at a time.

GIT-L01 gave us blobs: content without paths. A blob alone cannot reproduce a project. Each step below adds exactly one missing relationship and explains the problem that forced it to exist, how it is stored, and how it fails. Click through all six.

Step 1 · Tree

A blob cannot describe a folder listing

GIT-L01 established that a blob holds content but not its path. A snapshot must still say which paths exist, which object supplies each file’s content, which entries are directories, files, executables, or symbolic links, and how nested folders are represented. A tree supplies that structure.

Example: git ls-tree HEAD prints one line per entry: mode, type, object ID, name.

The whole picture, assembled

Two commits, one branch, one HEAD. The labels C1, C2, T1, T2, TB, TF, B2 belong to this drawing; they are not literal Git IDs.

branch ref: refs/heads/main ───────► commit C2 │ ├── tree ─────► tree T2 (project snapshot) │ ├── README.md ──► blob B2 │ ├── backend/ ───► tree TB │ └── frontend/ ──► tree TF │ └── parent ───► commit C1 │ └── tree ─────► tree T1 HEAD (branch-attached) ──symbolic ref──► refs/heads/main

Read it from the outside in. HEAD names the branch reference. The branch reference names commit C2. C2 names tree T2, which is the whole project at that moment, and names its parent C1. T2 names a blob for README.md and subtrees for backend/ and frontend/. Only the first two arrows are names that can be moved. Each object link is part of the hashed payload: changing it normally changes the object ID, subject to hash-collision assumptions.

Inside the mechanism

Why nesting trees is cheap: structural sharing

Suppose you change only frontend/src/App.jsx. Git writes a new blob for it. The src tree now lists a different blob ID, so it is a new tree with a new ID. That forces a new frontend tree, which forces a new root tree. But the backend tree did not change at all, so the new root tree simply repeats the old backend tree ID. For one newly stored file payload, that path can require a blob and updated ancestor trees; any already-existing identical objects are reused. Everything else is reused by ID, not copied.

This is a Merkle tree: a tree in which each node’s ID is a hash over its children’s IDs. Because a commit names a root tree and its parents by ID, the commit ID transitively covers the referenced Git object graph, not external submodule contents, LFS payloads, dependencies or build inputs.

Inside the mechanism

Why the index caches file metadata

To answer “what changed?” Git would otherwise have to re-read and re-hash every file on every git status. Instead each index entry stores the file’s object ID next to the stat information Git saw when it last hashed the file: modification and change times, device and inode numbers, size, and mode. If those still match, Git assumes the content is unchanged and skips hashing.

This cache has a known edge, which Git’s documentation calls racy Git: a file modified within the same timestamp granularity as the index write could look unchanged by its metadata. Git detects that window and re-checks those entries by content. The lesson: the index is a performance structure as well as a staging list, and its shortcuts are deliberately conservative.

Keep this mental picture: Objects (blob, tree, commit) are immutable and addressed by IDs computed from their bytes. Names (branch refs, tags, HEAD) are small, mutable pointers to those IDs. Local state (working tree, index) is scratch space that becomes an object only when you write it. Almost every confusing Git situation is two of these three categories being mistaken for each other.

Part 3 · The incident

“We deployed main.” Nobody can say which main.

Here is the situation this lesson exists to prevent. A teammate runs the test suite, sees it pass, and writes in the release note: “deployed main, tests green.” Two days later staging shows a bug that the tests should have caught. The teammate is sure the fix was in. Someone else is sure it was not. Both are reading real evidence; neither has evidence about the same object.

First, decode the terms in that story:

Commit ID

The object ID of a commit: a hash over the commit object’s bytes, which include its tree ID and parent IDs. It identifies one snapshot plus its ancestry, permanently.

Branch

A reference under refs/heads/. Each new commit made on it moves it forward. “main” on Monday and “main” on Wednesday are usually different commits.

Tag

A reference under refs/tags/, conventionally used for a release. It is expected not to move, but nothing in the reference itself prevents it.

Remote-tracking ref

A local copy such as refs/remotes/origin/main, recording where the remote’s branch was the last time you fetched. It can be stale.

Artifact digest

A content hash of a built output, such as a container image’s sha256:… digest. Like a commit ID, it names exact bytes; unlike a commit ID, it says nothing about source unless you record the link.

Image tag such as latest

A movable label in a container registry. Like a Git branch, it is a convenience name that can point at different digests over time.

Inspect each statement: what does it truly prove?

Open each card. Ask: “Is this about an object, a name, or local state? What claim would go beyond that evidence?”

0 of 7 opened. Click the evidence cards. Notice that only one is about an object, and even that one proves less than it seems.

Important reasoning rule: Do not argue about whether “the fix was in main.” Resolve every name to an object ID at the moment it was used, and compare IDs. Two people holding different IDs are not disagreeing about the fix; they are looking at different versions. If nobody recorded an ID, the honest answer is “we do not know which version passed,” and the fix is to record it next time.

Part 4 · Four strengths of “this version”

A folder, a name, an ID, and a vouched-for ID are four different claims.

When someone says “this version,” they are pointing with one of four kinds of handle. Each level adds a different kind of evidence, not an automatic guarantee of correct scope or trust, and evidence for one level does not automatically give you the next. Click each level to see what it is made of inside Git and the trap that comes with it.

Level 01 · Local state

Local state

The working tree and the index belong to one clone on one machine. They have no ID until you write them into objects. Two engineers can each have a “clean” checkout and still be on different commits.

Example: “It works in my folder” is a statement about a directory, not a version.
Inside a tag

Lightweight and annotated tags are different things

A lightweight tag is just a ref under refs/tags/ holding a commit ID, exactly like a branch that nobody advances. An annotated tag (git tag -a) first writes a tag object into the object database. That object records the ID and type of the object it tags, the tag name, a tagger line with a timestamp, a message, and optionally a signature. The ref refs/tags/v1.0 then points at the tag object, not at the commit.

That is why git rev-parse v1.0 can print one ID while git rev-parse 'v1.0^{}' prints another: the second form peels the tag, following it to a non-tag object, not necessarily a commit. Use ^{commit} to require a commit. When you record a release, record the peeled commit ID, and keep the tag object ID if you verify its signature.

Inside a name

How Git resolves a short name, and how that goes wrong

When you type v1, Git searches in a documented order: $GIT_DIR/v1 (used for names such as HEAD), then refs/v1, refs/tags/v1, refs/heads/v1, refs/remotes/v1, and refs/remotes/v1/HEAD. The first match wins. If a branch and a tag share a name, the tag wins and Git prints a warning that the refname is ambiguous.

Short commit IDs have a similar trap. Git accepts any unique prefix of an object ID, and prints abbreviated IDs that are unique today. As a repository gains objects, a prefix that was unique when someone pasted it into a ticket can later match more than one object. Use full names (refs/tags/v1) and full IDs in anything a machine or an auditor will read later.

Verification means resolving names at the boundary. A human may say “main” or “v1.4.0.” A pipeline should immediately resolve that name to a full commit ID with git rev-parse --verify, use that ID for every later step, and write it down. From that point on, a moved name cannot change what you built.

Part 5 · Mechanism controls

Six habits that keep objects, names, and local state apart.

A control here is a deliberate practice or guardrail that stops one category of Git state from being mistaken for another. Each one exists because a specific failure is possible. Each card states the first-principles question it answers, how Git supports it internally, and what it does not guarantee.

01

Inspect with supported commands

Ask Git, not the files inside .git.

First-principles question: Which program actually knows the current value of this object or name?

Git’s on-disk layout is an implementation detail. A ref may be a loose file such as .git/refs/heads/main, a line in .git/packed-refs after git pack-refs, or an entry in the newer reftable format (git init --ref-format=reftable). Objects may be loose files or entries inside compressed pack files. Reading or editing these files by hand gives wrong answers as soon as the storage changes, and can corrupt a repository.

  • git cat-file -t and -p show an object’s type and content.
  • git ls-tree lists a tree; git ls-files --stage lists the index.
  • git rev-parse, git show-ref, and git symbolic-ref resolve names.
  • To move a ref, use git update-ref, git branch, or git commit, never a text editor.
What it guarantees

You see what Git itself will use, whatever the storage format.

What it does not

It answers for this clone only. Another clone, or the remote, can hold different refs.

02

Resolve names to full IDs at the boundary

Turn every human name into an object ID once, early.

First-principles question: If this name moves in the next minute, will my build or my record change?

A pipeline that runs git checkout main twice, minutes apart, can check out two different commits. Resolve once, then pass the ID. git rev-parse --verify 'refs/heads/main^{commit}' fails loudly unless the name resolves to exactly one commit. In GitHub Actions, GITHUB_SHA depends on the event: a pull_request run commonly uses a synthetic merge commit, not the contributor head. Record the event and actual checked-out HEAD, and verify the source intended for that run.

  • Use full 40-character (SHA-1) or 64-character (SHA-256) IDs in records.
  • Peel tags with ^{commit} before recording.
  • Fail the build if the name is ambiguous or missing.
What it guarantees

Every later step works on one immutable snapshot, whatever happens to the name.

What it does not

It does not prove the name pointed at the right commit when you resolved it. That is a trust question (control 05).

03

Update refs with compare-and-swap

Move a name only if it still points where you think.

First-principles question: What if someone else moved this ref between my read and my write?

A ref update is a read-modify-write. Git makes it safe with locking and an expected old value. The files backend creates <ref>.lock, checks the current value, writes the new value, and renames the lock into place. git update-ref refs/heads/main <new> <old> refuses with “cannot lock ref … is at X but expected Y” if the ref has moved. A push works the same way: the client sends old and new IDs for each ref, and the server rejects an update that is not a fast-forward unless forced.

  • Prefer git push --force-with-lease=<ref>:<expected-id> over --force.
  • Use git push --atomic when several refs must move together or not at all.
  • On the server, deny non-fast-forward updates and deletions on shared branches.
What it guarantees

No silent lost update: a concurrent change makes your update fail instead of erasing theirs.

What it does not

A bare --force-with-lease compares against your remote-tracking ref, which a background fetch can update without you seeing the new commits.

04

Keep the three states honest

Know which state your build actually read.

First-principles question: Did the thing I tested come from a commit, or from whatever happened to be on disk?

A build tool reads the working tree, not the commit. If the tree has uncommitted edits or untracked files, the artifact contains something no commit records. git status --porcelain gives a stable, script-friendly status; an empty result means no tracked file differs from HEAD and no untracked, non-ignored file exists. git describe --dirty appends -dirty to its output when the working tree has modifications, which makes the problem visible in a version string.

  • Build from a fresh checkout of a resolved ID in CI.
  • Fail or mark the build if the tree is dirty.
  • Remember untracked ignored files are normally omitted from status but can still affect a build; tracked files are not made invisible by ignore rules, and --ignored shows ignored paths.
What it guarantees

The artifact’s inputs are the committed tree, which anyone can check out again by ID.

What it does not

It does not pin inputs outside Git: base images, package registries, compilers, or the network.

05

Make release names hard to move and easy to verify

Protect tags; sign what you publish.

First-principles question: Who is allowed to change what “v1.4.0” means, and how would a consumer detect it?

A tag is a ref, so anyone with push rights and --force can move it unless the server forbids it. Git’s own manual says a published tag should never be re-pointed: if you tagged the wrong commit, use a new name, because otherwise two people can both have “version X” and hold different X’s. Hosting platforms provide rules that restrict tag updates and deletions. Separately, git tag -s and git commit -S sign the unsigned object payload, excluding the signature itself, then embed or append the signature; git tag -v and git verify-commit check it.

  • Never re-point a published tag; publish a new one.
  • Restrict who can create, move, or delete release tags.
  • Verify signatures against a key list you control, not just any valid key.
What it guarantees

Successful verification is evidence that the corresponding private key signed the unsigned payload under the selected signature scheme and trust policy, and so, through the hash chain, this tree and its history.

What it does not

It does not prove the code is safe, the key was not stolen, or that the signer reviewed every change.

06

Record the release chain

Link source ID to artifact digest to running workload.

First-principles question: Starting from what is running, can I walk back to the exact commit, and from the commit forward to every artifact?

A commit ID and an image digest are both strong identifiers, but nothing connects them unless the build records the connection. Write the commit ID into the artifact’s metadata (for example the OCI annotation org.opencontainers.image.revision), keep a build record that maps run, commit, and digest, and deploy by digest. Supply-chain frameworks such as SLSA formalize this as signed provenance: a statement of which builder produced which artifact from which source.

  • Source commit ID → workflow run → tests and artifacts → image digest(s) → deployed revision.
  • Each link must be recorded at the time, not reconstructed from memory.
What it guarantees

You can answer “which commit is running?” with evidence instead of recollection.

What it does not

A recorded link is only as trustworthy as the system that wrote it. Unsigned metadata can be edited.

Part 6 · Worked example from first principles

Build one commit by hand, and watch each object appear.

In daily work, git add and git commit do everything below for you. Doing it once with Git’s lower-level plumbing commands removes the magic: you see that a commit is assembled from the index, through a tree, into a commit object, and only then given a name. Run this in a throwaway directory, never in the course repository. The blob and tree IDs below were checked for these exact bytes in SHA-1 format. Identity/time lines are illustrative, not captured session output; your commit ID can differ. The mkdir guard refuses an existing demo directory.

$ mkdir demo && cd demo && git init -b main $ git config --local user.name "Demo" $ git config --local user.email "demo@example.invalid" $ mkdir backend && echo "# app" > README.md && echo "print(1)" > backend/main.py $ git add . $ git ls-files --stage 100644 e2bd1550b11947a1bcbec6a139dc428f93a47d33 0 README.md 100644 b917a726c93f902e43291d9009d6488385133b67 0 backend/main.py $ git write-tree 6b8b63bb6a541778186b43d26d9a00576bcf9688 $ git ls-tree 6b8b63bb 100644 blob e2bd1550b11947a1bcbec6a139dc428f93a47d33 README.md 040000 tree fecabd4c47112bad84fb2043e1986130030dabb7 backend $ git symbolic-ref HEAD refs/heads/main $ git rev-parse --verify -q HEAD; echo "exit $?" exit 1 $ c=$(git commit-tree 6b8b63bb -m "first commit, by hand") $ git update-ref refs/heads/main "$c" "" $ git cat-file -p "$c" tree 6b8b63bb6a541778186b43d26d9a00576bcf9688 author Demo <demo@example.invalid> 1794112801 +0530 committer Demo <demo@example.invalid> 1794112801 +0530 first commit, by hand
Concept 1

The index is flat; trees are nested

git ls-files --stage shows the index as a flat, sorted list of full paths: backend/main.py is one entry, with no separate entry for backend/. Each line has a mode, a blob ID, a stage number (0 normally; 1–3 appear only while a merge conflict is unresolved, a Week 3 topic), and a path.

git add already wrote the blobs into the object database. That is why content you staged but never committed can still be found later as an unreferenced object. git write-tree then folds the flat list into nested trees, one per directory, and prints the root tree’s ID. The index stores a cache of tree IDs for unchanged directories, so on a large repository Git only rebuilds trees for directories that changed.

Concept 2

Tree entries: mode, type, ID, name

Each stored tree entry records mode, name and binary object ID; the displayed type is inferred from the mode. The modes you will meet are 100644 (regular file), 100755 (executable file), 120000 (symbolic link, whose blob holds the link target), 040000 (subtree), and 160000 (a gitlink: a commit ID in another repository, used by submodules).

Entries are stored in a fixed sorted order, so identical directory content always produces the identical tree ID. Git tracks files, not directories: an empty directory has no entry in the index, so ordinary add/commit do not preserve it; plumbing can explicitly construct an empty subtree. Changing only a file’s executable bit changes its tree entry, and so the tree ID, without changing the blob.

Concept 3

A commit is text that names a tree

The commit object is a short text record: a tree line, one parent line per parent (none here, because this is a root commit), author and committer lines with a Unix timestamp and a time-zone offset, optional extra headers such as a signature, a blank line, and the message. Its ID is the hash of exactly these bytes.

That makes the commit ID deterministic. Running the same commit-tree twice within the same second, with the same identity, produces the same commit ID. A second later the timestamp differs, so the ID differs, even though the tree is identical. This is why two commits can have different IDs while their tree IDs are the same: git commit --allow-empty deliberately creates exactly that.

Concept 4

Naming is a separate, conditional step

Before update-ref, the commit existed but nothing named it. HEAD already said refs/heads/main, yet git rev-parse --verify HEAD failed: main was an unborn branch, a name with no target yet.

The empty third argument to git update-ref means “only create this ref if it does not exist yet.” Running the same command again fails with “reference already exists.” That is a compare-and-swap: name the object only if the name is in the state I expect. git commit does the same thing internally, using the current commit as the expected old value.

The key deduction: A commit is not a diff. It references a complete tree snapshot and its parent commit(s). When you run git diff HEAD^ HEAD, Git compares two trees and computes the difference on demand; because unchanged subtrees have identical IDs, it can skip them without reading them. Here HEAD^ means the first parent. Do not generalize that to merge-parent rules yet; that is part of the next module, and the gitrevisions reference documents the full syntax.

Follow the reasoning for the second commit

Now edit README.md and commit normally. Predict each observation before you run it, then check.

Edit the file

After editing README.md, git status --short prints M README.md: a blank left column (index equals HEAD) and M in the right column (working tree differs from index). git rev-parse HEAD still prints the same commit ID. Editing a file changes neither the commit nor the branch.

Stage it

git add README.md hashes the new content, writes a new blob, and replaces that one index entry. Status now prints M README.md: the change moved to the left column. git diff (working tree versus index) is empty; git diff --staged (index versus HEAD) shows the change. The branch has still not moved.

Commit it

git commit writes a tree from the index, writes a commit object whose parent line is the old HEAD commit ID, and then updates refs/heads/main from the old ID to the new one. HEAD itself was not rewritten; it still names refs/heads/main.

Compare the trees

git rev-parse 'HEAD^{tree}' 'HEAD^^{tree}' prints two different root tree IDs. But git rev-parse HEAD:backend HEAD^:backend prints the same ID twice: the backend subtree was reused, not copied.

Name the release

git tag -a v1.0 -m "release" writes a tag object and points refs/tags/v1.0 at it. git cat-file -t v1.0 prints tag; git rev-parse 'v1.0^{commit}' prints the commit ID. git describe prints v1.0; after one more commit it prints something like v1.0-1-g9c313a8: the nearest tag, how many commits since, and g plus an abbreviated commit ID.

Check the history of the name

git reflog lists every value HEAD has had in this clone, newest first, with the operation that moved it. The reflog is local, not shared, and it is how you find a commit that no branch names anymore. The earlier commit object remains addressable through its ID and through the new commit’s parent link.

Important distinction: The plumbing commands are for understanding and for scripts. In the course lab you use git add and git commit, and inspect the created tree rather than manually editing the index or building internal object bytes. Never edit files under .git to change a branch.

Part 7 · From symptom to diagnosis

“Which source is actually running?” Walk the chain backwards.

Return to the incident. Staging shows a bug that the teammate says was fixed in “main.” A diagnosis must be an explanation supported by observations, not a story about who is right. The useful move is to start from the thing that is definitely real (the running workload) and walk back, link by link, towards a commit ID.

Intervention

Redeploying “latest,” re-running the pipeline on main, or force-pushing a “fixed” tag all change the system. Each one also destroys the evidence of which version was running, and each resolves a movable name again, possibly to yet another commit.

Observation

Reading the image digest the cluster actually pulled, the build record for that digest, the commit ID it names, and the content of that commit changes nothing. Each answer narrows the next question.

A useful release chain records five links. This chain is only valid if each link is actually recorded and checked. A branch name alone is none of these links.

1. Describe the symptom exactly

“Staging returns the old error on /api/status at 14:05.” Record the environment, time, and the observed behavior, not “the fix is missing.”

2. Find the running artifact’s digest

Read the digest of the image actually running, not the tag in the manifest. If the manifest says app:latest, the tag was resolved to a digest when the image was pulled; that digest is the fact.

3. Map the digest to a commit ID

Look up the build record or the image’s revision annotation for that digest. If neither exists, record that gap: the chain is broken here, and no amount of arguing about main repairs it.

4. Ask Git about that exact commit

Run git cat-file -p <id> and git merge-base --is-ancestor <fix-commit> <id>. The second command exits 0 if the fix commit is in the deployed commit’s history. This answers ancestry only. A later revert can undo an ancestral fix, and a cherry-pick can apply it under another ID; inspect the deployed tree and test the behavior.

5. Explain the divergence

If the fix is not an ancestor, find out why the build used that commit: the pipeline re-resolved a branch late, the tag was moved, a stale cache served an old latest, or the teammate’s fix was never pushed. Each hypothesis has a distinct observation.

6. Fix the record, then the release

Deploy by digest from a build of a known commit ID, and add the missing link to the pipeline so the next investigation takes one command, not one afternoon.

Part 8 · The operating contract

Eight questions before you call something “a version.”

This checklist exists because each item names a specific way the wrong object gets built, tested, or shipped. Open each one to see its purpose and the evidence that answers it.

01 · Which category is this: object, name, or local state?

Every confusing Git report mixes categories. Blobs, trees, commits, and tag objects are objects with IDs. Branches, tags, and HEAD are names. The working tree and index are local state. Decide which one you are holding before you draw a conclusion.

Evidence: git cat-file -t <thing> for objects; git rev-parse --symbolic-full-name <thing> for names.
02 · Is the working tree clean, and does that matter here?

A build reads files on disk. Uncommitted or untracked files produce an artifact that no commit describes, and ignored files are invisible to status yet still visible to the build.

Evidence: empty git status --porcelain output, or a version string from git describe --dirty without -dirty.
03 · Which name was resolved, when, and in which clone?

“main” resolves differently in your clone, on the remote, and in CI, and differently over time. Remote-tracking refs are a snapshot from your last fetch.

Evidence: the full ID from git rev-parse --verify at the moment of use, or git ls-remote for the remote’s current value.
04 · Is the identifier full-length and unambiguous?

Abbreviated IDs can become ambiguous as a repository grows, and short ref names can match both a branch and a tag.

Evidence: a full commit ID and a fully qualified ref such as refs/tags/v1.4.0 in every machine-read record.
05 · If a tag names the release, can it move, and was it verified?

Tags are refs. A moved tag silently changes what every later checkout of that name means.

Evidence: a server-side rule that blocks tag updates, the peeled commit ID recorded at release time, and a git tag -v result against a trusted key list.
06 · Was every ref update conditional on the expected old value?

Unconditional force-pushes can erase someone else’s commits from a branch, and server audit and receive policies determine what is recorded or rejected.

Evidence: pushes with --force-with-lease=<ref>:<expected-id>, protected branches that reject non-fast-forward updates, and an audit log of forced updates.
07 · Which artifact digest came from which commit ID?

A commit ID and a digest are each strong, but the link between them exists only if the build records it.

Evidence: a build record or org.opencontainers.image.revision annotation mapping digest to commit, ideally as signed provenance.
08 · Could someone else rebuild or re-inspect exactly this version next month?

Reproducibility needs the commit ID, the objects still reachable on the remote, and the inputs that Git does not track.

Evidence: the commit is reachable from a protected branch or tag on the shared remote, and non-Git inputs (base image digests, lockfiles) are pinned.

Part 9 · At production scale

One clone forgives. Thousands of clones, pipelines, and teams do not.

Everything so far used one repository on one laptop. A real organization has one shared remote written to by hundreds of engineers and bots, thousands of clones and CI runners each holding their own copy of every ref, mirrors in several regions, and release pipelines that turn names into artifacts many times an hour. The object model does not change at scale: objects are still immutable and names are still movable pointers. What changes is how many independent places resolve a name, how many writers race to move it, and how many consumers trust whatever it resolved to. Each card is a failure mode that only appears, or only becomes dangerous, at that scale.

Failure mode · Mutable release names

A tag that everybody pins is moved under them

Mechanism: A tag is a ref, so anyone with push rights to it can re-point it with a forced push unless the server forbids it. Consumers that reference a release by tag name re-resolve that name every time they fetch or run. In March 2025, the widely used GitHub Action tj-actions/changed-files was compromised: according to GitHub’s advisory, attackers retroactively modified multiple version tags to reference a malicious commit, and workflows that used the action by tag ran code that printed CI secrets into workflow logs. Nothing about any existing commit changed. Only names moved, and that was enough. Container image tags such as latest or 1.4 behave the same way one layer further out.

What operators see: builds that changed behavior with no change in their own repository; the same pipeline definition producing different results on different days; a dependency’s tag whose peeled commit ID differs from the one recorded last week.

Production control: reference third-party code and images by full commit ID or digest, not by tag. GitHub’s secure-use reference recommends pinning actions to a full-length commit SHA, because changing what that reference means would require a SHA-1 collision for a valid Git object. For your own releases, block tag updates and deletions on the server, never re-point a published tag, and record the peeled commit ID next to every tag you publish.

Failure mode · Ref update races on a busy remote

Two writers, one name, one lost update

Mechanism: Moving a ref is a read-modify-write. A push sends “change refs/heads/main from old ID A to new ID B,” and the server applies it only if main is still A. On a busy branch, someone else often lands first, so a normal push is rejected as non-fast-forward and the pusher must fetch, integrate, and retry. That is the system working. The danger is the workaround: git push --force relaxes client-side fast-forward protection; it does not bypass the protocol old-ID check or server policy. It can still replace remote ancestry that the pusher has not integrated. Even --force-with-lease without an explicit expected value compares against your remote-tracking ref, and Git’s manual warns that a background git fetch (an IDE, a cron job) can update that ref so the lease passes while you have never seen the new commits. Pushes that move several refs are applied per ref unless you ask for --atomic, so a release push of a branch and a tag can half-succeed.

What operators see: commits that “disappeared” from main but still exist by ID in someone’s reflog; release branches where the tag landed but the branch update did not; bursts of rejected pushes and retries when many bots push to one branch.

Production control: reject non-fast-forward updates and deletions on shared branches on the server. When a force is legitimate, use --force-with-lease=<ref>:<expected-id> (and consider --force-if-includes). Use --atomic for multi-ref releases. Serialize high-contention integration through a queue rather than letting every writer race.

Failure mode · Provenance gaps

The artifact came from a version no commit describes

Mechanism: A build tool reads the working tree, and a pipeline resolves names whenever its scripts happen to. Three common gaps break the commit-to-artifact link. First, a dirty or partially updated workspace on a reused runner produces an artifact with no matching commit. Second, a job that resolves main at the start, then runs git fetch and git checkout main again later, can test one commit and package another. Third, for pull_request events GitHub documents GITHUB_SHA as the last merge commit on refs/pull/<number>/merge: a test merge of the pull request into its base branch, which may never exist on any branch after the real merge. The artifact is real; the commit it claims may be one nobody else can find.

What operators see: a running image whose recorded revision is unknown to the shared remote; a “tested” commit ID that differs from the one in the release notes; two builds of “the same commit” with different digests.

Production control: check out a resolved commit ID into a clean workspace, fail on a dirty tree, and pass that one ID through every step. Stamp it into the artifact (for example org.opencontainers.image.revision) and publish signed provenance, as described by SLSA, that ties builder, source commit, and artifact digest together. Treat any artifact without that link as unverifiable rather than probably fine.

Failure mode · Supply-chain trust

The author line is whatever the client typed

Mechanism: The author and committer lines in a commit object are written by the committing client from its own configuration and environment. Anyone can create a commit claiming to be anyone, and the object will be perfectly valid. A signature (git commit -S, git tag -s) signs the unsigned payload: a commit embeds a signature header, whereas an annotated tag appends a signature. The signature itself is excluded from the signed payload. Because those bytes include the tree ID and parent IDs, a valid signature on one commit or tag transitively covers the whole snapshot and its entire ancestry, through the hash chain. That is also why the strength of the hash function matters: GIT-L01’s object IDs are what the signature actually binds.

What operators see: commits attributed to maintainers who did not write them; signatures that verify cryptographically but with a key nobody on the team recognizes; “Verified” badges that prove a key matched an account, not that the change was reviewed.

Production control: require signed commits or signed release tags on protected refs, and verify against a key list you control (for SSH signatures, Git’s gpg.ssh.allowedSignersFile). Remember what a signature does not prove: that the code is safe, that the key was not stolen, or that anyone reviewed the change. Pair signatures with protected branches and required review, which are Week 4 topics.

Failure mode · Version skew across clones and teams

Every team has “v1.4.0”. Not every team has the same one.

Mechanism: Each clone, CI cache, and mirror holds its own copy of every ref, updated only when it fetches. Since Git 2.20, git fetch rejects updates to existing tags unless forced, which deliberately protects you from a moved tag but also means that after a tag is moved, clones that fetched before and after the move keep different objects under the same name, indefinitely. Git’s own git tag manual describes exactly this outcome: two people both have “version X” but different X’s. Mirrors replicate asynchronously and can lag. Abbreviated commit IDs pasted into tickets years ago can become ambiguous as a monorepo grows. A branch and a tag with the same short name resolve to the tag, with only a warning.

What operators see: teams that agree on a version name and disagree on its behavior; bug reports that cannot be reproduced on “the same version”; tooling that resolves a short ID to one object on one machine and errors as ambiguous on another.

Production control: exchange full commit IDs and digests between teams, not names. When a name must be used, compare git rev-parse 'v1.4.0^{commit}' against git ls-remote output for the authoritative remote. Monitor mirror lag. Forbid branch and tag names that collide.

Failure mode · Clock skew and ordering

Commit dates are claims, not an ordering

Mechanism: Author and committer timestamps come from the committing machine’s clock and can be set to any value through the environment. Rebasing and cherry-picking keep the original author date but set a new committer date. Across thousands of machines with imperfect clocks, commit timestamps are not a reliable order of events, and certainly not proof of when code reached the shared remote. The only order Git guarantees is ancestry: parent links define ancestry, not trusted wall-clock time or proof of when each object was physically stored.

What operators see: “newest” commits that are older than their parents by timestamp; release tooling that picks the wrong “latest” commit by date; incident timelines that contradict the push logs.

Production control: use ancestry as one clue about history, then check the tree and behavior for the fix (git merge-base --is-ancestor), not dates. Answer “when did this reach the remote?” with the server’s push or audit logs, which use the server’s clock, not the commit header.

Scale changes the meaning of “the same version.” On one laptop, a name and an ID are interchangeable for a few minutes. Across an organization, a name is resolved independently by every clone, runner, mirror, and registry, at different times, by different writers. The only identifiers that mean the same thing everywhere, forever, are full object IDs and content digests. Every other identifier is a request to go and look something up, and the answer depends on who looks and when.

Part 10 · Practice the reasoning

Do not memorize the vocabulary. Make the next decision.

Choose an answer before opening the explanation. Every scenario turns on the same skill: deciding whether you are holding an object, a name, or local state, and what that lets you conclude.

Scenario 1 · “Deployed main”

A release note says only “deployed main.” What is the strongest improvement?

Reasoning: main can point at a different commit tomorrow. A commit ID identifies a commit object, and the artifact digest ties what was built and deployed back to it, provided each link is actually recorded and checked. A date identifies nothing, and HEAD is just the current checkout context of one clone, so it moves too.

Scenario 2 · Same tree, different commit

Two commits have exactly the same top-level tree ID, yet their commit IDs differ. Which explanation is correct?

Reasoning: A commit is a hash over its own bytes: the tree line, every parent line, author and committer metadata, and the message. git commit --allow-empty creates exactly this case. Commit IDs are not random: the same bytes produce the same ID, which is why two identical commit-tree calls in the same second agree. Ignore rules do not remove tracked content from a tree. Equal tree IDs identify matching recorded trees under the same object format and integrity assumptions; ignored untracked build inputs remain a separate concern.

Scenario 3 · An edit before a commit

You edit README.md and have not run any other command. What has changed?

Reasoning: Verify it: git rev-parse HEAD prints the same ID as before, while git status --short shows M README.md, with the change in the right-hand (working tree) column. Staging updates the index; committing writes new objects and then moves the branch. HEAD names a branch, not your folder.

Scenario 4 · HEAD, main, and an ID

In branch-attached state, git symbolic-ref HEAD prints refs/heads/main. Which statement is accurate?

Reasoning: There is one commit and two levels of naming. A new commit moves refs/heads/main; HEAD keeps naming the branch, so it follows automatically. Option D describes detached HEAD, a different state that Week 3 explains.

Scenario 5 · A pinned action changes behavior

Your workflow uses a third-party action as some-org/some-action@v3. Without any change in your repository, it starts doing something new. What is the most likely mechanism, and the right control?

Reasoning: A tag or branch is a movable name, and it is resolved again on every run. Moving it requires only push rights, which is how the 2025 tj-actions/changed-files compromise worked. Commit objects did not change, so neither a hash collision nor cache corruption is needed to explain it. Pinning a full commit ID turns a name you trust into an object you can verify.

Scenario 6 · Which object maps a path to content?

Which object tells Git that certain bytes are the content of src/App.jsx?

Reasoning: A blob holds content only, with no path, so identical bytes at two paths share one blob. The path is spelled by a chain of tree entries from the root tree down. A commit names only the root tree, and a branch names only a commit.

Why a graph of objects instead of dated snapshot folders?

A folder-copy design is easy to imagine: save the whole project folder for every release. Git instead represents content, directory structure, snapshots, ancestry, and names as linked objects and references. This supports content reuse and makes the relationships inspectable. Read every mechanism step without scripting

A blob cannot describe a folder listing

GIT-L01 established that a blob holds content but not its path. A snapshot must still answer: which paths exist, which object supplies each file’s content, which entries are directories, files, executables, or symbolic links, and how nested folders are represented. A tree object supplies that structure. Each stored entry records mode, name and object ID, with the displayed type inferred from the mode, and an entry can reference a blob or another tree (a subtree). Entries are kept in a fixed sorted order, so the same directory content always hashes to the same tree ID. Inspect a real tree with git ls-tree HEAD, and a subtree with git ls-tree HEAD:frontend when the commit’s top-level tree contains a directory named frontend; in another repository, substitute an actual directory.

root tree → blob README.md, tree backend (→ blob main.py, blob pyproject.toml), tree frontend (→ blob package.json, tree src → blob App.jsx, blob main.jsx). This shape is conceptual, not a claimed listing from every starter-app version. Failure it prevents: two files with identical bytes at different paths would be indistinguishable without a tree; with one, they share a blob and differ only in tree entries.

The index is the input to a tree that will be recorded

The index, often called the staging area, is the set of entries Git will use to construct the next snapshot. Inside, the usual full-index representation is a binary file (Git resolves its location; split index and sparse index are supported): a header with the signature DIRC (“dircache”), a version number, and an entry count, then one entry per path, sorted by path, each holding cached file metadata (times, device, inode, mode, size), the blob ID, flags including a 2-bit merge stage, and the path; then optional extensions and a checksum. git add hashes working-tree content, writes the blob, and updates that path’s entry. git write-tree writes the index state as a tree object and returns the tree’s ID.

working tree ── git add ──► index (staging area) ── git write-tree ──► tree object. In the lab you use git add and git commit; Git performs the tree creation as part of making the commit. Failure mode: a second Git process that finds .git/index.lock already present refuses to run (“Unable to create … index.lock: File exists”), because two writers to one index would corrupt the staged snapshot.

A commit object records a snapshot and ancestry

A commit is not a bag of changes. It references one top-level tree and, for non-root commits, one or more parent commit IDs. It also carries author and committer lines (name, email, Unix timestamp, time-zone offset) and a message. A root commit has no parent line; a normal single-parent progression has one; merge commits can have several, which Week 3 explores. Because the commit’s ID is a hash over all of this, including the parent IDs, a commit ID pins the entire history behind it.

tree <tree-object-id> / parent <parent-commit-id> / author <name> <email> <timestamp> / committer <name> <email> <timestamp> / blank line / <commit message>. A diff is derived by comparing snapshots: git diff HEAD^ HEAD. Here HEAD^ means the first parent; do not generalize that to merge-parent rules yet.

References give useful names to object IDs

Remembering a 40-character object ID is inconvenient, so Git uses references (refs): names that resolve to object IDs. A local branch such as main is the ref refs/heads/main, naming a commit. Unlike a commit object, the reference can move: after a new commit on main, the branch advances, and the earlier commit stays addressable through its ID and through the new commit’s parent link. Moving a ref is done under a lock and, when an expected old value is given, only if the ref still holds it.

Inspect with git show-ref --heads, git rev-parse refs/heads/main, and git rev-parse HEAD. In the standard branch-attached state after a commit, HEAD and refs/heads/main resolve to the same commit ID. Do not edit .git/refs/heads/main to move a branch: refs may live in loose files, packed-refs, or reftable, so use Git’s supported commands.

HEAD identifies the current checkout context

In an ordinary branch-attached checkout, HEAD is a symbolic reference: its value is the name of another ref, not an object ID. In the files backend, .git/HEAD contains the line ref: refs/heads/main. git symbolic-ref HEAD prints refs/heads/main in the lab after initializing main and committing. This two-level naming is why committing moves the branch and HEAD follows without being rewritten. HEAD is not an alias for the working-tree directory, and it is not a copy of every file.

Detached HEAD, where HEAD names a commit directly rather than a branch ref, is mentioned only so the model allows for it. Week 3 explains how checkout, branch pointers, and history movement create different states; do not start branch-creation or recovery operations yet. In a new repository, HEAD can name an unborn branch that has no commit yet.

Three states you must not collapse

Working tree: the files currently checked out and editable. Index: the content prepared for the next commit. Committed tree: the snapshot a commit references. An edit in the working tree does not alter the index or an existing commit; staging updates the index; a new commit records a new snapshot. git status --short shows two of the comparisons at once: the left column is index versus HEAD, the right column is working tree versus index. git diff compares working tree with index; git diff --staged compares index with HEAD.

Edit README.md and status shows “ M README.md”; stage it and it shows “M README.md”; edit again and it shows “MM README.md”: three different versions of one file, in three places, at once. Try it in the model below.

Read every evidence category without scripting

Local state

The working tree and the index belong to one clone on one machine. They have no object ID until you write them into objects with git add (blobs) and git commit (trees and a commit). Two engineers can each have a “clean” checkout and still be on different commits, and a build that reads a dirty working tree produces an artifact that no commit describes.

“It works in my folder” is a statement about a directory, not a version. git status --short tells you whether the folder matches HEAD, not which commit HEAD is.

Movable name

Branches, HEAD, tags, remote-tracking refs, and registry tags such as latest are all names that are looked up at the moment you use them. The answer depends on which clone or registry you ask and when. Branches are designed to move. Tags are conventionally fixed, but a tag is still a ref, and a forced push can re-point it unless the server forbids it.

Monday’s “main” and Wednesday’s “main” are usually different commits. A pipeline that resolves “main” twice in one run can test one commit and ship another.

Object ID

A full commit ID is computed from the commit object’s bytes, which include the root tree ID and the parent IDs. Change any file, any path, any mode, any ancestor, or any metadata and you get a different ID. So the ID identifies one exact snapshot plus its entire history, on every machine, forever. Use the full ID, not an abbreviation, wherever a machine or an auditor will read it later.

git rev-parse --verify 'v1.4.0^{commit}' turns a tag into the commit ID it names right now. Record that ID; from then on, moving the tag cannot change what you built.

Vouched-for ID

An object ID tells you exactly what, but not who or how. Two additions close that gap. A signature on a commit or annotated tag, verified against keys you trust, shows that a specific key holder signed that exact object. Signed build provenance records which builder produced which artifact digest from which commit ID. Together they let a consumer check the chain instead of trusting a name.

git tag -v v1.4.0 verifies the tag object’s signature; the tag names a commit ID, which names a tree, so the signature covers the whole snapshot. It still does not prove the code is safe or that the key was not stolen.

Reference · Plain-English glossary

Git’s words, without the assumed knowledge.

Use this section whenever a word feels like jargon. Search by a term or a phrase. For each word, ask which category it belongs to: object, name, or local state.

32 terms
Abbreviated object ID

A unique prefix of a full object ID, such as 9c313a8. Git accepts it if it is unique in this repository now; as the repository grows, it can become ambiguous. Use full IDs in durable records.

Ancestry

The relationship formed by parent links. Commit A is an ancestor of B if you can reach A by following parents from B. git merge-base --is-ancestor A B tests it. It is the only ordering Git guarantees.

Annotated tag

A tag created with git tag -a or -s. It writes a tag object recording the tagged object’s ID and type, the tag name, a tagger line, a message, and optionally a signature; the ref under refs/tags/ points at that tag object.

Artifact digest

A content hash of a built output, such as a container image’s sha256:… digest. It identifies exact bytes but says nothing about source unless a build record links it to a commit ID.

Blob

An object holding one file’s content bytes, with no name or path. Identical content anywhere in the history shares one blob.

Branch

A reference under refs/heads/ that names a commit and advances when you commit on it. A movable name, not an immutable version.

Commit

An object recording one root tree ID, zero or more parent commit IDs, author and committer lines with timestamps, optional headers such as a signature, and a message.

Compare-and-swap (ref update)

Changing a ref only if it still holds an expected old value. git update-ref <ref> <new> <old>, normal pushes, and --force-with-lease all use this idea to prevent lost updates.

Detached HEAD

A state where HEAD names a commit directly rather than naming a branch ref. Explained in Week 3.

Fast-forward

Moving a ref from commit A to commit B where A is an ancestor of B, so no commit is dropped from the branch’s history. Servers reject non-fast-forward pushes unless forced.

Force-with-lease

A git push option that forces an update only if the remote ref still has an expected value. Safest with an explicit value: --force-with-lease=<ref>:<expected-id>.

Gitlink

A tree entry with mode 160000 that records a commit ID from another repository. Submodules use it.

HEAD

The name of your current checkout context. In branch-attached state it is a symbolic ref to the current branch, such as refs/heads/main. Not the working-tree directory and not a copy of the files.

Index (staging area)

The index (normally .git/index, with split/sparse/worktree variations): a sorted representation of paths, each with a mode, blob ID, stage number, and cached file metadata. It is the content of the next commit. git add updates it; git ls-files --stage shows it.

Lightweight tag

A tag that is only a ref under refs/tags/ holding an object ID, with no tag object, tagger, message, or signature.

Loose refs, packed refs, reftable

Ways Git can store refs: one small file per ref, many refs in a single packed-refs file, or the newer reftable format. Use Git commands, not file reads, because the storage varies.

Merkle tree

A tree where each node’s ID is a hash over its children’s IDs. Git’s trees and commits form one, so a commit ID transitively covers every file and every ancestor.

Object ID

The hash of an object’s type, size, and content, used as its name: 40 hex characters with SHA-1, 64 with SHA-256. The same bytes always produce the same ID.

Peeling

Following a tag object to the object it tags, repeatedly if needed. v1.0^{} or v1.0^{commit} peel a tag to its commit.

Plumbing and porcelain

Plumbing commands (write-tree, commit-tree, update-ref, cat-file) do one low-level step each and have stable output for scripts. Porcelain commands (add, commit, status) combine them for people.

Provenance

A record, ideally signed, stating which builder produced which artifact from which source commit and inputs. SLSA defines a standard format.

Racy Git

The edge case where a file changes within the timestamp granularity of the index write, so its cached metadata looks unchanged. Git detects that window and re-checks the content.

Reference (ref)

A name under refs/ (or a special name such as HEAD) that resolves to an object ID or to another ref. Refs are mutable; objects are not.

Reflog

A local log of the values a ref or HEAD has had in this clone. Not shared with other clones. Useful to find commits that no ref names anymore.

Remote-tracking ref

A local ref such as refs/remotes/origin/main that records where the remote’s branch was at your last fetch. It can be stale; git ls-remote asks the server directly.

Revision expression

Syntax that Git resolves to an object, such as HEAD^ (first parent), HEAD~2, HEAD^{tree}, or HEAD:frontend. Documented in gitrevisions.

Root commit

A commit with no parent line, usually the first commit in a repository.

Signed commit or tag

A commit or tag object carrying a signature over its unsigned payload, excluding the embedded or appended signature, created with -S or -s and checked with git verify-commit or git tag -v. Proves a key holder signed that object, not that the code is safe.

Symbolic ref

A ref whose value is the name of another ref rather than an object ID. HEAD is the common example; git symbolic-ref reads and sets it.

Tree

An object storing mode, name and object ID per entry; tools infer the displayed type from the mode. Entries point at blobs, subtrees, or gitlinks. A tree has no message or ancestry.

Unborn branch

A branch name that HEAD refers to before any commit exists for it, as in a new repository. Commit-inspection commands have nothing to show yet.

Working tree

The checked-out files you edit. Changes here are not recorded until you stage and commit them, and builds read from here.
