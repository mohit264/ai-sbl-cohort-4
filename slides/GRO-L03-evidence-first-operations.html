GroundOps · Lesson 03 · Evidence-first operations

“Something is broken” is not yet a root cause.

An investigation becomes unreliable when a guess silently turns into a fact. Keep uncertainty visible while deciding what to observe and what to change.

Pause & predict

The page loads; a teammate says “restart the API,” while another says curl to port 8000 returns the expected body. Predict an observation that distinguishes a stopped API from a browser using another address. Write what each explanation predicts before opening the comparison.

Compare your reasoning

Observe the browser's actual URL and result, then compare a direct request from the same machine to the intended API. A response at 8000 can coexist with a browser targeting 8001. Restarting before observing may erase evidence without changing that wrong target. If both callers target 8000, investigate another boundary rather than forcing the port explanation.

50 teaching minutes · draft. Core: prediction, labels, ladder, worked case, safe action and transfer. Fleet-scale details are extension/reference reading. Novice timing remains unmeasured.

Interaction scope: cards show authored reasoning, not a live system. They send no API requests. Worksheet completion is not verification; text is neither graded nor saved nor sent, and disappears on reload. Clear note and quiz reset support another attempt.

The central question.

How do we move from a symptom to a justified repair without guessing, avoidable disruption or premature success? You need only GRO-L01's vocabulary and GRO-L02's request path.

01 · Name the claim

Separate observation, inference, hypothesis, test, cause, fix, verification, and prevention.

02 · Weigh the evidence

Climb the system-state ladder and know which rung each check supports.

03 · Act proportionately

Choose the smallest safe next action, preserve useful evidence, and record what you did not test.

Mapped model and its limits

A parcel marked “delivered” but missing from the recipient maps to a claimed success with an unmet outcome. A time-stamped scan maps to an observation; “next building?” to a hypothesis; comparing label and destination to a discriminating test; redirecting and confirming receipt to correction and user verification. Network requests can be copied, retried and cached, and logs can be incomplete. This analogy labels claims, not packet behavior.

Part 1 · Begin with the real-world promise

What does a “justified repair” actually require?

Picture the course starter app. The React page loads in your browser. The card that should show the API status says it could not fetch the status. Within thirty seconds someone in the chat says, “The backend is down, just restart it.” That sentence sounds like a diagnosis. It is actually a guess about the cause, wrapped around a proposed intervention, with no observation attached. This lesson is about everything that should sit between the symptom and that restart.

The promise

What “fixed” should mean

When we say an incident is fixed, we are promising four things at once: we know what caused the failure in the scope we investigated; we changed the smallest thing that removes or mitigates that cause; we checked that the user-visible behavior is back and nothing obvious broke; and we did something that makes a repeat less likely or less harmful.

If any of the four is missing, the honest word is not “fixed.” It might be “mitigated,” “restored, cause unknown,” or “changed, not yet verified.”

The engineering question

Which claims are we actually entitled to make?

Every sentence in an investigation is a claim. “The API is down” is a claim. “The request went to port 8001” is a claim. Some are observed directly, some are inferred, some are just guesses. The engineering skill is not to stop making claims—it is to label each one honestly, so nobody builds a repair on top of a guess they mistook for a fact.

The same discipline scales from a local lab to a production incident. Not every failure needs a formal postmortem, but every failure deserves claims that match their evidence.

First principle: An investigation is a chain of claims. Each claim is only as strong as the evidence beneath it. A guess that silently becomes a “fact” weakens every claim built on top of it—including the final “fixed.”

Eight verbs people quietly collapse into one

Under pressure, people say “I checked,” “it’s the network,” and “fixed it” as if they were the same kind of statement. They are not. Learn these labels; you will use them in every lab note and incident record from now on. The ninth card, mitigation, is the word people most often confuse with a fix.

01

Observation

A directly recorded signal, with a time and a scope: who saw it, from where, with which tool.

“At 10:14:07 the browser request to http://127.0.0.1:8000/api/status failed with a connection error.”

02

Inference

A conclusion supported by one or more observations. It goes beyond what was recorded, so it can be wrong even when every observation is right.

“The failure appears to be before a valid HTTP response was received.”

03

Hypothesis

A testable explanation. It must predict something you could check and might find false.

“The API is not listening on port 8000.”

04

Test

An action chosen because its result would differ depending on which hypothesis is true.

curl -i http://127.0.0.1:8000/api/status, while watching the API process terminal.

05

Root cause

The causal condition the evidence demonstrates was responsible—in the investigated scope. Finding one failed setting is not always the full organizational root cause.

“For this run, the frontend requested the wrong port.”

06

Fix

The change that removes or mitigates the demonstrated cause—scoped to what the evidence showed, not to a broader guess.

“Set the development API base URL back to port 8000.”

07

Verification

Evidence that the expected behavior is restored and no known regression was introduced. Re-run the check that originally failed, plus a check for what the fix could break.

“The browser now requests port 8000 and the card renders the body.”

08

Prevention

A change to tests, configuration validation, automation, documentation, monitoring, or ownership that reduces recurrence or impact. Never just “be more careful.”

“Add a browser test asserting the frontend calls the expected API path.”

Plus · Mitigation

Mitigation

An action that reduces user harm now without necessarily touching the cause. Restarting, rolling back, or disabling a feature are mitigations until evidence shows they addressed the cause.

“Restarted the API; status card works again; cause still unknown.”

Why the verbs collapse

Humans are story-building machines. Once a plausible story appears (“the backend is down”), every new detail gets read as support for it, and the moment it was a guess is forgotten. Time pressure makes this worse: a confident sentence feels like progress. Labels interrupt the slide. Writing “hypothesis:” in front of a sentence reminds everyone that it still needs a test.

What the labels buy you

Labels make an investigation auditable: another engineer can read your note and see which claims rest on recorded signals and which rest on reasoning. They make it resumable: if you hand off at 3 a.m., the next person knows what has been ruled out. And they make the final claim bounded: you say exactly what you proved, no more.

Part 2 · Derive the mechanism

A diagnostic loop: one falsifiable hypothesis at a time.

If guesses are the problem, we need a procedure that makes each guess earn its place. The loop below is used in every FailureCore lab in this course. Each step exists because skipping it produces a specific, recognisable mistake. Click each step to see what it does and how it fails.

Loop step 1 · Symptom

State the symptom exactly

Write down the user-visible behavior, time, environment and version if known. “The status card shows a fetch failure at 10:14 on the local stack” can be compared with evidence. “The API is down” already assumes a cause.

Example: preserve the actual error, not a paraphrase that turns a symptom into a diagnosis.

Why “falsifiable” is the key word

A useful hypothesis predicts an observation that might contradict it. “The browser targets 8001 rather than the intended listener at 8000” predicts the Network URL. A current file saying 8000 does not alone refute it: the page might contain a stale value or an inherited override. A missing log is supporting evidence only within known logging coverage. Test the effective request rather than treating every indirect clue as decisive.

Why one controlled comparison at a time

If two settings change and the symptom disappears, either, both or an unrelated change may explain recovery. That is confounding. A team may retain a timeout increase, restart and cache flush as a ritual because nobody knows which mattered. Holding other conditions fixed costs some speed but makes the causal explanation stronger; it still cannot rule out every contributing condition.

Why observe before you intervene

A restart can discard memory, open connections and loaded settings. A rebuild can replace the bundle being investigated. Existing logs or files may survive, but do not assume they will. Prefer relevant low-risk observations before mutation when safe. Even a diagnostic HTTP request adds load and logs; read-only describes intended application effects, not literally zero side effects.

Why it is a loop, not a line

A result that contradicts a prediction is useful. Check whether the observation and the hypothesis refer to the same caller, version and time; then revise or reject the explanation. Record contradictions rather than explaining them away. A passing test supports a bounded explanation, not certainty about all networking.

Keep this mental picture: every hypothesis is a prediction machine. Before testing, write what each candidate predicts. If all predict the same result, find a different observation or state why the next check only narrows part of the uncertainty.

Part 3 · The incident

The page loads. The status card fails. Six pieces of evidence arrive.

This illustrative case assumes the page at http://127.0.0.1:5173, an API listener at 8000, no listener at 8001 and no simultaneous changes. Six statements arrive: observations, configuration and a teammate's claim. None is a captured course run.

Network panel

The browser's request record: URL, method, result and timing. Open it before the click and check filters/recording before interpreting silence.

curl -i

A terminal HTTP client; -i includes response headers. It tests from the shell's location without enforcing browser CORS.

Listener

A network endpoint accepting connections for a process. A running process is not automatically listening on the expected interface and port.

Access log

A server's request record under its logging configuration. Check source, time, filtering, delay and retention before relying on an absent line.

Base URL

The address prepended to an API path. Here VITE_API_BASE_URL can override the default http://127.0.0.1:8000.

Connection error

No HTTP response was received by this caller. That differs from 404 or 500, which indicate an HTTP response; the exact error still matters.

Inspect each statement: what does it prove, and what does it not?

Before revealing each card, name its instrument, caller and strongest justified claim. Then compare the limit.

0 of 6 opened. Combine different vantage points; a reveal count is not verification.

Follow the disagreement: the actual browser target is 8001 while the intended route responds at 8000. That is a more specific lead than “networking is broken.” It does not establish why the setting became wrong or prove other environments healthy.

Part 4 · The system-state ladder

Evidence at one rung does not prove the rung above it.

Part 3’s evidence came from different instruments, and each instrument can only see so high. This ladder makes that explicit. It moves from low-level facts (“the file exists”) to the only claim users care about (“the feature works for me, under my conditions”). Click each rung to see what it claims, what evidence supports it, and the false conclusion it tempts people into.

Rung 1 · Artifact present

The required code or configuration exists

There is a thing you can point at: a file diff, a commit, a built bundle, an image in a registry. Evidence: the diff, the commit ID, registry metadata. This is the cheapest rung to check and the one most often mistaken for the top of the ladder.

Example: “The env file says port 8000, so the browser uses 8000.” The file can be correct while the running dev server still serves values it read before the edit.

Place Part 3’s evidence on the ladder

The env file (Evidence 05) is rung 1. The uvicorn terminal (Evidence 03) is rung 2. The curl call (Evidence 02) reaches rungs 3 and 4—but only from the terminal’s vantage point. The browser’s failed request (Evidence 01) is a failed rung 3 from the browser’s vantage point. Put that way, the contradiction is obvious: rung 3 succeeds from one place and fails from another. The two calls are not reaching the same address.

Why each rung is a separate claim

Each rung adds a new way to fail that the rung below cannot see. A file cannot tell you whether a process loaded it. A process cannot tell you which port it bound. A listener cannot tell you which route answers. A route cannot tell you whether a browser may read it. Moving up a rung always needs a new observation; it never follows by logic alone.

Vantage point is part of the rung

Rungs 3 to 6 are always “from where?” The same URL can be reachable from your terminal and unreachable from a browser, a container, or another region, because each caller has its own network namespace, DNS view, proxy settings, and security rules. A rung claim without a vantage point is incomplete.

Time is part of the rung too

Every observation was true at a moment. A curl call at 10:14 says nothing about 10:20 if a deployment, restart, or config reload happened in between. Good notes record when each rung was observed, so nobody stitches together a “healthy system” from checks taken at different times against different versions.

RungClaimTypical evidenceFalse conclusion to avoid
1 · Artifact presentRequired code/config existsFile diff, commit, registry metadata“The file exists, so it works.”
2 · Process startedRuntime process is aliveProcess output, process table, container status“The process runs, so the route is reachable.”
3 · Listener reachableCaller can connect to host/portTCP connection, direct HTTP check“The port is open, so correct behavior is served.”
4 · Route respondsMethod/path returns a responsecurl -i, API test, response body“200 means every response is semantically correct.”
5 · Contract holdsResponses match documented expectationsTests for status, schema, validation, error cases“The contract holds, so the browser can read it.”

This ladder is a teaching model, not an industry standard. It exists to stop evidence from being stretched. A real production-readiness claim may need extra rungs for authentication and authorization, persistence, performance, resilience, accessibility, data protection, deployment safety, and business invariants. The rule stays the same: name the rung your evidence reaches, and do not claim the one above it.

Part 5 · Choose the smallest safe next action

Maximize information. Minimize risk. In that order of thought.

The loop says what to do next in the abstract. This part is about the concrete action you are about to type. A useful diagnostic action tells you as much as possible about which hypothesis is true, while changing as little as possible about the system and the people relying on it. Before running anything, answer six questions. Each question exists because skipping it has burned real teams.

01

Plausible hypotheses

What explanations are still on the table?

Why it exists: an action chosen without a list of hypotheses is a ritual, not a test. Writing the list also shows when you have only one idea, which is the moment you are most likely to be wrong.

  • Wrong API port in the frontend configuration.
  • API process not listening, or listening on another interface.
  • Browser blocked from reading the response (CORS).
  • Stale bundle: the browser is running code built before a config change.
Strong

Three or four specific candidates, each tied to a boundary from GRO-L02.

Weak

“Something with the network or maybe the backend.”

02

Expected results

If each hypothesis were true, what would I see?

Why it exists: without a written prediction, any result can be read as confirmation afterward. Predictions turn an action into an experiment.

  • Wrong port → Network panel shows :8001; API log stays silent.
  • Not listening → curl to :8000 gets “connection refused.”
  • CORS → request reaches the API log; Console shows a CORS error.
Strong

One distinct prediction per hypothesis, written before the action.

Weak

“Let’s see what happens.”

03

Discriminating observation

Which action separates the hypotheses?

Why it exists: some checks feel productive but cannot change your mind. Pick the one whose result differs across the candidates.

Opening the Network panel and reading the request URL separates “wrong port” from “not listening” and from “CORS” in one look. Running curl again from the terminal cannot: it never sees the browser’s URL.

Strong

An observation from the vantage point that is actually failing.

Weak

Re-running the check that already passes, because it is reassuring.

04

State change

Does this action change the system?

Why it exists: state-changing actions destroy evidence and can create new failures. A restart clears in-memory state and a crashed process’s exit status; a rebuild replaces the bundle you were trying to inspect; a cache flush erases the stale entry that explained the symptom.

Prefer read-only actions until the cause is narrow enough to justify a change.

Read-only

Network panel, logs, curl, process status, config diff, running version or image digest.

State-changing

Restart, rebuild, redeploy, cache flush, delete, permission change, data migration.

05

Exposure and blast radius

Could it expose data, destroy work, cost money, or affect others?

Why it exists: diagnostic commands are not automatically safe. Printing an environment dumps secrets into a terminal recording. Widening CORS to * “to test” can expose an API to every website. Restarting a shared service drops other people’s connections. Scaling up to “rule out load” has a bill.

Ask

Who else is on this system? What would leak into logs, screenshots, or chat?

Prefer

The narrowest scope: one request, one test user, one instance, a redacted output.

06

Rollback or cleanup

Is there a safe way back?

Why it exists: if you cannot undo an action, you must be much more certain before taking it. Some effects survive any rollback: a deleted volume, a sent email, a published package, a rotated credential that other services still use.

Before acting

Write the exact undo step and check it is possible.

If there is none

Escalate, get a second pair of eyes, or find a reversible alternative.

The process might have exited on invalid configuration, crashed on a request, been killed for using too much memory, or never imported a dependency. Part 6 · Worked example from first principles

From “the card fails” to a bounded cause, one recorded step at a time.

Here is the whole loop applied to Part 3’s incident. Notice how each step names its evidence and its limits. The aim is not speed; it is a final claim that nobody can knock over, because every piece of it was observed or tested.

10:14:07 browser GET http://127.0.0.1:8001/api/status → (failed) net::ERR_CONNECTION_REFUSED 10:15:30 terminal $ curl -i http://127.0.0.1:8000/api/status HTTP/1.1 200 OK content-type: application/json {"service":"groundops-api","status":"available","version":"0.1.0", ...} 10:15:30 uvicorn INFO: 127.0.0.1:53122 - "GET /api/status HTTP/1.1" 200 OK (no uvicorn line at 10:14:07)

The exact browser error text and the API body vary by browser and starter-app version. The shape is what matters: one failed request with no HTTP response, one successful request from a different vantage point, and a server log that saw only the second.

Symptom

The React page loads at http://127.0.0.1:5173; the API status card shows a fetch error. Recorded at 10:14, local dev stack, current working tree.

Observation 1 — browser vantage point

The Network panel shows GET http://127.0.0.1:8001/api/status failing with a connection error: no status code, no headers.

Observation 2 — terminal vantage point

curl -i http://127.0.0.1:8000/api/status returns 200 OK and the expected JSON body. The API is answering on 8000 from this machine.

Hypothesis

The frontend is configured with the wrong API port. Prediction: configuration says 8001; the API log has no line for the click.

Discriminating test

Inspect the configured API base URL and compare it with the Network panel URL and the known listener. In the starter app the value comes from VITE_API_BASE_URL, with a fallback of http://127.0.0.1:8000.

Result

The frontend env file sets port 8001. The API log shows the curl line but nothing at 10:14:07. Both predictions hold, and logging is shown to work, so the missing line is meaningful.

Root cause, bounded

For this run, the frontend requested the wrong port, so the intended API route was never targeted. Not “networking is broken.” Not “the API is flaky.”

Fix

Correct the development base URL to port 8000, then restart the Vite dev server, because Vite reads env files at start-up and replaces import.meta.env values in the code it serves.

Verification

Reload the page. Confirm the Network panel now shows :8000, the response status, and an Access-Control-Allow-Origin header matching the page origin, and that the card renders the body. Note the time and the commit you verified.

Prevention

Add a check that fails loudly when the frontend targets an unexpected API URL—a start-up log of the effective base URL, or a browser integration test that asserts the request path. Keep the URL in documented environment configuration, and never place a secret in a VITE_ variable: those values ship in the public bundle.

What the evidence does not justify: “all networking is healthy,” “the API was never the problem anywhere,” or “this will not happen in staging.” It justifies a narrow, bounded conclusion about one failure on one stack and its repair. Narrow claims are not weak claims; they are the only kind that survive scrutiny.

Write the incident note as you go

The note is not paperwork after the fact. Filling it in during the investigation forces each claim into the right field. Type into the fields below as you work a practice incident. Nothing is graded, saved, or sent anywhere.

Incident note

“Tests not executed” is on this list on purpose

It stops absence of evidence from silently becoming evidence of success. If you did not check the browser after the fix, write that down; the next reader needs to know.

Part 7 · Review AI-generated artifacts as executable decisions

Valid YAML is one gate. It is not the only gate.

An AI-generated Dockerfile, Kubernetes manifest, GitHub Actions workflow, or shell script is not documentation. It is a proposal that, once merged, will run—with whatever permissions, secrets, and network access it is given. Review it the way you would review a production change written by a capable stranger who has never seen your environment. Syntax validity, linting, and “it looks reasonable” answer none of the questions below.

# Proposed by an assistant: "deploy preview on every PR" on: pull_request permissions: write-all jobs: preview: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - run: echo "API_TOKEN=${{ secrets.API_TOKEN }}" >> .env - run: ./scripts/deploy-preview.sh

This parses, lints, and would probably “work.” Hold it against the matrix and it fails several dimensions at once: every job gets every write permission, a secret is copied into a file that later steps or artifacts might expose, and nobody has said what the deploy script touches or how to undo it.

01 · Intent

Does it solve the requested requirement?

Generated code often solves a nearby problem. “Deploy a preview” is not the same as “deploy to the shared staging environment,” and a script that does the second while named the first will pass review if nobody reads it.

02 · Context

Does it match this repo and environment?

Check repository layout, runtime and action versions, port mappings, base images, and deployment topology. Assistants fill gaps with common defaults; your environment is not the common case.

03 · Permissions

Does it ask only for the authority it needs?

Workflow token permissions, cloud roles, and Kubernetes RBAC should be scoped to the job. GitHub’s secure-use guidance recommends granting the GITHUB_TOKEN the least access required. write-all fails this dimension on sight.

04 · Secrets and data

Could anything sensitive leak?

Look for keys, tokens, personal data, or internal URLs that could land in source, logs, image layers, build caches, artifacts, or a browser bundle. Any VITE_ variable used by client code ships to every visitor.

05 · Failure behavior

What happens when things go wrong?

Timeout, unavailable dependency, invalid configuration, non-2xx response, restart mid-way, partial failure. Generated scripts usually cover the happy path. Ask what state is left behind when step 3 of 5 fails.

06 · Observability

Would you know if it worked or failed?

Which signal shows success? Which exposes failure? Can the on-call operator actually see those signals, or do they live in a log nobody has access to?

07 · Reversibility

Can it be undone?

Reverting a commit does not unsend an email, un-publish a package, restore a dropped table, or revoke a token that leaked. Name the side effects that survive rollback.

08 · Verification

What exact evidence will prove it worked?

Before merging, write the check you will run afterward and which ladder rung it reaches. “The workflow went green” is rung 1–2 evidence about the workflow, not about the preview a reviewer will open.

AI can help with every row of this matrix—it can list permissions, spot a secret in a log line, or draft failure handling. What it cannot do is own the decision. A team must decide what evidence is enough, approve risky permissions, and stay accountable for what runs. “The assistant generated it and CI passed” is not an answer to any of the eight questions.

Part 8 · From symptom to diagnosis

“Resolved by restart” is a mitigation, not a root cause.

Change the incident: this time the API really stopped, a restart restores the card, and the cause remains unknown. Predict what evidence could separate a startup failure from a process killed during operation before reading the alternatives.

Intervention

Restart, rollback or a setting change deliberately changes state. Sometimes this must come first to limit harm. It can erase evidence and adds a new change to explain; record what happened before and after.

Observation

Read the stopped process's exit status, last log lines, prior memory readings, version and loaded configuration where available. Some survive a restart and some do not. Preserve inexpensive evidence when safe; do not assume every log is lost or complete.

Four different explanations to test

Invalid configuration

A required setting may be absent or invalid at startup. Restarting unchanged inputs need not help. Look for the startup error and whether the replacement process read different inputs.

Process-level failure

A fatal runtime or native-code failure can terminate a worker. An ordinary FastAPI request exception generally produces a 500 response, not worker death. Require process exit evidence as well as a traceback before claiming a crash. A request failure and a stopped listener are different boundaries.

Resource pressure

An out-of-memory kill may terminate a process; CPU starvation may instead leave it alive but slow. Restart can reduce memory temporarily without fixing a leak. Compare resource history and actual termination records.

Missing dependency

An import can fail or a required downstream service can be unavailable. A restart helps only if the relevant condition changed or transient state cleared. A port already occupied is a binding conflict, not evidence a dependency returned. Inspect the specific error.

1. Protect users within the incident process

Use an authorized mitigation when harm is ongoing. Say what it restores and what remains unknown.

2. Capture inexpensive, perishable evidence

Preserve available error lines, exit status, version and time without exposing secrets or delaying urgent recovery.

3. Verify the mitigation

Repeat the original user action, not only curl. Record the observed restored outcome and time.

4. Investigate with discriminating predictions

Compare configuration, process-level failure, resource pressure and dependency hypotheses against captured observations. Several may contribute.

5. Correct the demonstrated condition and track prevention

Choose an appropriate validator, error-handling change, resource control or dependency check. Give the work an owner and observable completion criterion; writing it down does not mean it ran.

Evidence-first is not “never act.” User safety wins over an expensive investigation. Record “restored; cause unknown” when that is all the evidence supports, and keep the cause investigation separate. Local labs can pause before mutation; production incidents may not.

Part 9 · The operating contract

Eight questions before you write “resolved.”

This is the checklist to run before closing any investigation, from a lab to a production incident. Each question exists because a specific, common mistake slips past without it. Open each one to see its purpose and the evidence that answers it.

01 · Is every claim labelled with its verb?

Observations, inferences, hypotheses, and tested results should be distinguishable on the page. An unlabelled sentence is read as fact by the next person, whatever it actually was.

Evidence: the note separates “observed (source, time)” from “inferred” and “hypothesis.”
02 · Which ladder rung does each check reach, and from where?

A check proves its rung from its vantage point at its moment—nothing above, nowhere else, no later.

Evidence: each verification names its rung, its vantage point (browser, terminal, other service), and its time.
03 · Did the discriminating test actually discriminate?

If every hypothesis predicted the same result, the test confirmed nothing, however good it felt.

Evidence: written predictions per hypothesis, and the result that eliminated the others.
04 · Is the root cause bounded to what was demonstrated?

“Networking,” “human error,” and “the API was flaky” are not causes. A bounded cause names the condition, the scope, and the run.

Evidence: “For this run in this environment, condition X caused Y,” plus the evidence chain.
05 · Was the fix the smallest change that addressed the cause?

Several simultaneous changes make it impossible to know which one mattered and can bring in new risk.

Evidence: one change tied to the cause, or a written reason for each extra change.
06 · Was the original failing check repeated from the original vantage point?

Verifying with curl when the failure was in the browser verifies something else.

Evidence: the same user-visible check now passes, tied to the version and time verified.
07 · Are mitigations labelled as mitigations?

“Restarted, works now” must not be written into the cause field. Mitigation and investigation can both be correct; they are different entries.

Evidence: separate “mitigation” and “root cause” fields; cause marked “unknown” if not yet shown.
08 · Is there a specific prevention, and are untested things listed?

“Be more careful” is not an engineering control. And anything not tested must be written down, so absence of evidence is not read as success.

Evidence: a test, validator, alert, or runbook change with an owner and done-when, plus a “tests not executed” list.

Part 10 · At production scale

More evidence does not automatically mean a clearer explanation.

The worked case had one browser, one API and one nearby log. A service spread across many machines can produce sampled traces, aggregated metrics, differently timestamped logs and concurrent interventions. Not every system has all these properties. Identify which apply before interpreting the data. The diagnostic loop still asks what each observation supports, what it omits and what action would distinguish alternatives.

Failure mode · Averages hide a broken minority

A healthy average can conceal a failing cohort

Mechanism: aggregating healthy and broken groups can dilute a regional or version-specific error. In an illustrative population, a group carrying 3% of requests could fail completely while the global error rate is 3%. Whether that meets an SLO depends on the specified target. An acceptable mean latency can coexist with a long slow tail.

What operators see: a subgroup reports failures while a broad dashboard looks acceptable. “Intermittent” describes the observation, not its cause.

Control and cost: compare relevant version/location/client cohorts and latency percentiles with user outcomes. Choose useful metric dimensions with a cardinality budget; not every signal needs every label. More detailed logs and traces still carry privacy and retention costs. State the population covered rather than calling the whole fleet healthy.

Failure mode · Clocks and collection delays

A timestamp sort is not automatically causal order

Mechanism: host clocks can differ, and collection time can lag event time. Two retained events can appear reversed when sorted by wall-clock timestamps. A trace ID identifies related operations; it is not a timestamp or a value to sort for chronology.

What operators see: apparently earlier database errors are used to dismiss a deployment as a contributor, without checking clock uncertainty or which timestamp the tool displays.

Control and cost: correlate by trace/request ID, inspect parent-child span relationships and recorded send/receive events, and retain clock uncertainty. Parent links describe causal structure, not a total order of concurrent sibling spans. Maintain time synchronization and distinguish event time from ingestion time. W3C context propagation does not repair clocks or guarantee every span reached storage.

Failure mode · Missing or sampled evidence

No matching trace is an observation, not an explanation

Mechanism: head sampling decides before the operation's full outcome is known. A uniform probability sampler can drop rare errors like successes; other policies can use attributes already available at the start, so equal loss is not universal. Tail sampling can prefer errors or slow traces using later observations, but requires buffering and a decision policy. It cannot recover spans already dropped upstream.

What operators see: a request ID has no retained trace, or an available trace is incomplete. Possible causes include sampling, missing instrumentation, export failure, retention expiry, collection delay or a wrong search scope.

Control and cost: record the missing evidence as unknown until sampling or another loss mechanism is demonstrated. Inspect sampler/exporter configuration and health. Tail sampling consumes resources and can be overwhelmed; it does not guarantee every error survives. Keep suitable high-cardinality detail in access-controlled logs/traces rather than creating one metric time series per user.

Failure mode · Low-value alerts

Frequent non-actionable pages consume attention

Mechanism: internal events such as one process restart or high CPU may not mean users are failing. Paging indiscriminately on them can produce noise and reduce responder trust. Internal signals remain valuable for diagnosis and for actionable impending-risk alerts; they are not useless merely because they are not user symptoms.

What operators see: many pages require no action while consequential failures are first reported by customers.

Control and cost: connect paging to actionable user-visible reliability goals. The SRE Workbook gives multiwindow burn-rate examples, not universal thresholds. For its 30-day window, 720 hours total, a 14.4× burn rate for one hour corresponds to 14.4/720 = 2% of the budget under comparable request rates. Long/short windows balance sustained consumption and recent activity; traffic volume and business needs affect the choice.

Failure mode · Parallel interventions

Several repairs can confound the outcome

Mechanism: one responder restarts, another rolls back and another changes a flag. Each action can affect the others' observations. Recovery may establish that the combination helped without identifying each contribution.

What operators see: “something fixed it,” an uncertain causal account and a runbook retaining unnecessary changes.

Control and cost: Google's incident-management model separates coordination, operations and communications responsibilities. Adapt those roles to team size and authorization policy; do not imply one person must personally type every command. Keep a shared action/observation log, coordinate state changes and distinguish urgent mitigation from a controlled experiment. Coordination costs effort but makes parallel work interpretable.

Failure mode · Recovery discards useful state

Restoration can make later diagnosis harder

Mechanism: restarting or replacing an instance can discard memory, live connections and loaded settings. Persisted logs, source revisions or dumps may survive; a restart does not necessarily erase every crash record or make cause analysis impossible.

What operators see: service returns, but a useful failed-state observation is no longer available. State that limitation instead of filling the gap with a confident story.

Control and cost: under an authorized, rehearsed plan, capture inexpensive logs or isolate an affected instance without user traffic when safe. Dumps may contain credentials or personal data and require suitable access, retention and handling. Isolation can itself cost capacity. Never preserve a failing instance at the expense of urgent user safety; record what could not be collected and investigate surviving evidence.

Scope every “healthy” claim: which population, time window, instrument and collection policy? Evidence may support a fleet-level statement if its sampling and coverage justify that statement; one successful manual request does not automatically provide that coverage.

Part 11 · Practice the reasoning

Each answer should name the rung, the vantage point, or the verb.

These are the lesson’s exit-assessment questions, plus one at fleet scale. Choose an answer before reading the explanation. The aim is not to spot the “right” phrase, but to say exactly what the evidence does and does not establish.

Scenario 1 · A command exits with code 0

A CLI command returns exit code 0 after applying configuration. Is the service healthy?

Reasoning: the command’s success is evidence about the command: the configuration was accepted. It says nothing about whether a process loaded it, a listener is reachable, the route answers, or a user can complete the flow. It is useful evidence—just not evidence for the claim “healthy.” Climb the ladder with a check that reaches the rung you need.

Scenario 2 · curl works, the browser does not

curl to the FastAPI endpoint succeeds, but browser fetch fails with a CORS message in the Console. Does that prove the API is down?

Reasoning: a CORS error usually means a response arrived and the browser refused to let the page read it. The server can be up and reachable. The discriminating observation is the response’s Access-Control-Allow-Origin header compared with the page origin. Option D is an intervention that adds a security risk to answer a question a read-only check could answer.

Scenario 3 · Restart, and it works

The API process is restarted and the UI now works. Can the incident be closed with “resolved by restart” as the root cause?

Reasoning: restoring service is good and often right. But a restart resets state without explaining why the process stopped. Each candidate cause leaves different evidence (a start-up error, a traceback, an out-of-memory kill record, an import error). Record the mitigation, keep the cause field open, and investigate. “Monitor closely” is not a specific prevention.

Scenario 4 · A lint-clean workflow

An AI-created workflow asks for broad write permission. It uses correct YAML and passes linting. Should it merge?

Reasoning: lint passing establishes rung 1 for the workflow file. The review matrix asks whether the change is safe to run with real authority. Narrow the permissions to what the job needs, check where secrets flow, and write down how you will verify the outcome. Rejecting all generated workflows (C) is a blanket rule, not a review.

Scenario 5 · The fleet dashboard is green

Users in one region report errors. The fleet-wide error rate is 0.4%, within its target. A teammate says “metrics are fine, it must be their network.” What is the strongest next step?

Reasoning: the global rate is evidence about the whole population, not about the region in question. A per-cohort breakdown is read-only, cheap, and discriminating: it separates “their network” from “our instances in that region” from “one bad version.” Rolling back everywhere is a heavy intervention that may destroy the evidence.

Exit check

Write one bounded root-cause statement.

Use this shape: “For [scope], [condition] caused [symptom], shown by [evidence from which vantage point]. Not yet tested: [what remains].”

“For this run on the local dev stack, the frontend’s configured API base URL pointed at port 8001 while the API listened on 8000, so the status card’s request was refused—shown by the browser Network panel (request to :8001), curl from the terminal (200 on :8000), and an API access log with no line at the click time. Not yet tested: other browsers, and how the env file came to contain 8001.”

Reference · Plain-English glossary

Every term, without the assumed knowledge.

Use this whenever a word feels like jargon. Search by term or phrase. The goal is not memorization; it is knowing exactly what each word claims in the current situation.

32 terms
Observation

A directly recorded signal with a time and scope: which tool, from which vantage point, at what moment. Preserve its actual result before interpreting it.

Inference

A conclusion drawn from observations. It goes beyond the recorded signals and can be wrong even when those signals are accurate. Label it accordingly.

Hypothesis

A testable explanation that predicts observations a discriminating check might contradict. Surviving one check does not make it the only possible explanation.

Falsifiable

Able to be contradicted by a possible observation. “The browser requests port 8001” is testable; “something with networking” is too vague to guide a useful check.

Discriminating test

A check with different predicted results under different hypotheses. If both predict the same result, that check alone cannot distinguish them.

Root cause (bounded)

A causal condition demonstrated within the investigated run, environment and version. Multiple conditions may contribute; preserve what the investigation did not establish.

Mitigation

An action reducing harm without necessarily removing or establishing the cause. Restart or rollback can be appropriate while the cause remains unknown.

Fix

A correction addressing a demonstrated condition. A narrowly scoped change is usually easier to verify, but safety and dependencies determine the appropriate scope.

Verification

Evidence matching the required behavior, collected from the relevant caller and environment, with regression checks and untested conditions stated.

Prevention

A specific test, validator, alert, runbook or ownership improvement intended to reduce recurrence or impact. Give it an owner and observable completion criterion.

System-state ladder

The course's seven-rung teaching model, from artifact presence to required user outcome. Lower-level evidence alone does not establish higher-level behavior.

Vantage point

The caller and location of an observation: browser, shell, container, service or region. Different locations can have different routes and policies.

Listener

A network endpoint accepting connections for a program. Process existence alone does not show the expected interface/port is listening or reachable.

Access log

A server's request-handling record under its logging configuration. One logged control request shows some logging works, not complete coverage; missing lines need source, timing, filtering and retention context.

curl -i

A terminal HTTP request with response headers included. It tests from the shell's context and does not enforce browser CORS or verify React rendering.

Network panel

A browser tool recording requests and responses, including URL, method, status, headers and timing where available. Recording state and filters affect what you see.

CORS

A browser cross-origin response-reading mechanism using server headers. It is not authentication and a failed browser read does not by itself establish server unavailability.

Vite environment variable

A setting read at startup/build time. Inherited environment takes precedence over env files; VITE_-prefixed values exposed to client code must not contain secrets.

Exit code

A program's completion status; zero conventionally reports success according to that program's semantics. Determine which properties the command actually checked.

Incident note

A resumable account of symptom, observations, hypotheses, tests, bounded cause, mitigation, verification, uncertainty, prevention and unexecuted checks.

Tests not executed

Checks not run, explicitly recorded so a later reader does not mistake missing evidence for success.

Confounding

Multiple changing conditions obscure which caused an outcome. Controlled comparisons help separate effects; production mitigation may require broader action with that uncertainty retained.

Cohort

A group sharing a property such as version or region. Aggregate results can hide a failing group, so choose relevant comparisons.

Percentile (p95, p99)

A threshold in a distribution: approximately 99% of observations lie at or below p99. Estimates and ties depend on measurement method; it is not every user's latency.

Clock skew

Difference between clocks. Together with collection delay, it can make a timestamp-sorted account misrepresent event order.

Trace ID

A correlation identifier propagated through trace context. Join retained spans using it and examine parent-child relationships; the ID is not a sortable clock or proof of a complete trace.

Sampling

Selecting telemetry under a policy. Head sampling decides before the full outcome; tail sampling can use later information to prefer errors. Upstream loss, decision limits or overload can still omit errors. A missing record remains unknown until its loss mechanism is demonstrated.

Cardinality

The number of distinct values or combinations represented. Metric-label combinations create time series; unbounded user identifiers can consume substantial resources.

SLO and burn rate

An SLO is a reliability target for a defined measure/population/window. Burn rate compares current failure consumption with the rate allowed by its error budget.

Alert fatigue

Frequent non-actionable alerts can reduce responder attention. Prefer actionable signals tied to user harm or an important impending risk.

Incident commander

A coordinating role in an incident process, organizing responsibilities, priorities and communication. Authorization and change coordination must match the organization's procedure.

Least privilege

Grant only the authority the task requires, limiting damage from mistakes or compromise. Syntax validity does not justify broad permissions.

Mapped model and its limits

A parcel marked “delivered” but missing from the recipient maps to a claimed success with an unmet outcome. A time-stamped scan maps to an observation; “next building?” to a hypothesis; comparing label and destination to a discriminating test; redirecting and confirming receipt to correction and user verification. Network requests can be copied, retried and cached, and logs can be incomplete. This analogy labels claims, not packet behavior.

Changed condition

Predict: the env file says 8000 now, but Network still shows 8001. Did editing the file prove the running page changed? No: Vite loads env files at startup and inherited environment takes priority. Inspect only the relevant non-secret setting, restart the right process and reload. If the correct URL still fails, the port diagnosis does not cover the remaining fault.
