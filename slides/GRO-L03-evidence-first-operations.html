GRO-L03 · Evidence-First Operations

"Something is broken."
That is not yet a root cause.

An incident investigation becomes unreliable the moment a guess silently turns into a "fact." This lesson gives every step in between a name, so uncertainty stays visible instead of being quietly erased.

How do we move from "something is broken" to a justified repair — without guessing, causing avoidable disruption, or declaring success too early?

Not every failure needs a formal postmortem. The same discipline scales from a local lab to a production incident: make uncertainty visible, and don't invent certainty after the fact.

The System-State Ladder

Evidence at one rung does not prove the rung above it.

Click a rung to expand its evidence and the false conclusion it tempts people into.

Evidence: file diff, commit, artifact registry metadata.False conclusion to avoid: "The file exists, so it works."
Evidence: process output, process table, container status.False conclusion to avoid: "The process runs, so the route is reachable."
Evidence: TCP connection, direct HTTP check.False conclusion to avoid: "The port is open, so correct behavior is served."
Evidence: curl -i, API test, response body.False conclusion to avoid: "The route returns 200, so every response is semantically correct."
Evidence: tests for status, schema, validation, error cases.False conclusion to avoid: "The API contract holds, so the browser can read it."
Evidence: browser Network record + rendered UI state.False conclusion to avoid: "The UI works once, so capacity and reliability are adequate."
Evidence: acceptance test and product-level evidence.False conclusion to avoid: "One happy-path test proves production readiness."

This ladder is a teaching model, not a formal standard. A real production-readiness claim may need additional rungs for authentication, persistence, performance, resilience, accessibility, and business invariants.

Worked Case

The React page loads, the API status card fails

Reveal each step in order and watch the matching stage light up above.

  • Observation 1The browser Network tab shows the request is sent to http://127.0.0.1:8001/api/status.
  • Observation 2curl -i http://127.0.0.1:8000/api/status returns the expected body.
  • HypothesisThe frontend is configured with the wrong API port.
  • Discriminating testInspect the configured API base URL and compare it with the URL in the Network tab and the known API listener.
  • ResultFrontend config points to port 8001; backend logs show no matching request.
  • Root cause (bounded)For this run, the frontend requested the wrong port, so the intended API route was never targeted.
  • FixCorrect the development base URL to port 8000 and restart/rebuild the frontend as required by how the config is loaded.
  • VerificationConfirm the browser request now targets port 8000, inspect the response and Access-Control-Allow-Origin, and verify the UI displays the body.
  • PreventionAdd a startup/config check or browser integration test asserting the deployed frontend calls the expected API path. Keep the URL in documented environment config; never place a secret in a public client bundle.

Key Takeaways

Uncertainty stays visible. Certainty is earned.

  • Eight different verbs. Observation, inference, hypothesis, test, root cause, fix, verification, and prevention are not interchangeable.
  • The ladder doesn't skip rungs. Evidence one rung up does not establish the rung above it.
  • Falsifiable, not vague. "Something is wrong with networking" can't be tested; a specific port mismatch can.
  • Prefer read-only first. Maximize information, minimize risk, before mutating system state.
  • Syntax valid ≠ safe to merge. Review AI-generated artifacts against intent, context, permissions, secrets, failure behavior, observability, reversibility, and verification.
  • Mitigation ≠ root cause. A restart that restores service still needs a cause investigation afterward.
