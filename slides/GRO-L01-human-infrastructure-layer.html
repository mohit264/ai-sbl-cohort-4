Mapped model and its limits

A recipe maps to an artifact; an order specifying a meal and table maps to intended state; “the oven is on” maps to one observed fact; the correct meal reaching the customer maps to a verified outcome. A printed recipe does not prove delivery. Software can cache, retry and serve many callers at once; this analogy does not implement browser policy. Return to the actual caller, address, response and rendered result.

Part 1 · Begin with the real-world promise

What does “the feature works” actually mean?

Imagine a document app. You open a document and click a button labelled Summarize document. A few seconds later, a useful summary appears. That is the user outcome. The user does not care whether the code compiled; they care whether the promised task happened.

The promise

What the person expects

“When I click this button, the app will send my document for summarization and show me the result or a useful explanation if it fails.”

The engineering question

What must be true?

The button must respond. The browser must know where to send the request. The service must be reachable. The service must understand the request, do the work, and return a result the screen can display.

First principle: A feature is not a line of code. A feature is a promised outcome produced by a chain of parts working together.

Build the vocabulary from everyday language

A few words will appear throughout the lesson. Learn the simple meaning here; the glossary at the end gives fuller definitions.

Browser

The app you use to open websites, such as Chrome, Safari, or Firefox. It runs the visible screen and some code.

Frontend

The part of an application a person directly sees and interacts with: buttons, text, forms, menus, and screen behavior.

Backend / service

A program running elsewhere that performs work the screen should not or cannot do by itself, such as accessing protected data or calling an AI model.

API

A defined way for one program to ask another program to do something. Think of it as a service counter with agreed request and reply formats.

Patch

A proposed set of code or configuration changes. A patch is a proposal, not proof that the resulting application works.

Environment

The place and conditions where software runs: a developer laptop, a test system, or the live system customers use. Their settings can differ.

Part 2 · Derive the architecture

One click has to cross several boundaries.

A boundary is simply a point where work passes from one part of the system to another. Each hand-off creates a possible failure: the sender may use the wrong address, the receiver may be unavailable, or the reply may not be understood.

Boundary 1

The button and the promise

The person expects an action, not merely a button that looks clickable. The click handler must actually start the work and show progress or an error.

Possible failure: The button has no working action, or the click handler stops before sending anything.

Why “it works on my laptop” is weak evidence

Your laptop, browser, settings, and local services may be different from the environment a customer uses. A result on one computer only tells you about that computer and that attempt.

Why several parts are needed

The browser is good at drawing the screen. A backend may have access to private data, credentials, or expensive computing resources. They communicate because neither part is responsible for everything.

Keep this mental picture: The request must travel outward through the system, and the response must travel back. A failure at any hand-off can look like “the feature is broken.” We diagnose the hand-off; we do not guess at the cause from the symptom alone.

Part 3 · The incident

The pipeline is green. The user still sees an error.

Now we can make sense of the original incident. An AI assistant has suggested a new “Summarize document” button, a backend route, and a configuration value. The developer accepts the changes. The automated checks finish successfully. The page loads. But the user clicks the button and sees “Unable to reach the service.”

First, decode the terms in that story:

Git

A tool that records versions of code so a team can review and track changes. “The change exists in Git” means a version of the change was recorded.

CI / pipeline

CI means continuous integration. A pipeline is an automated sequence of jobs, often including tests and builds. Green means the jobs that ran reported success—not that every possible behavior was tested.

Build / artifact

A build turns source files into a package the next stage can use. The produced package is an artifact. It can be valid and still contain the wrong settings or behavior.

Deploy

To deploy is to make a particular version available in a target environment. A deployment command succeeding does not, by itself, prove every running component has the right version or works end to end.

Process

A process is a running instance of a program. A process can exist while the program's network listener, configuration, dependency, or user-facing behavior is broken.

Production

The live environment that real users depend on. A developer laptop or test environment can behave differently from production.

Important reasoning rule: Do not jump from “the feature failed” to “the backend needs a restart.” That is a guess about the cause. First collect an observation that can distinguish between plausible causes.

Part 4 · Four claims, four levels of evidence

“Running,” “reachable,” “healthy,” and “correct” are not the same claim.

Use this model for the rest of the course: Artifact → Intended State → Observed State → Verified Outcome. Click each stage to see its definition and a concrete trap. These are four different kinds of statements, and evidence for one does not automatically prove the next.

Level 01

An artifact exists

There is a thing we can inspect or move forward: source code, a built web package, a configuration file, or a container image. Existence tells us nothing yet about how it behaves in a real environment.

Example: A recipe can be printed and readable even before anyone cooks the meal. Having the recipe is not proof the meal was made correctly.

What is “intended state”?

It is the condition we want: for example, “the service should use the production API address and accept requests from this website.” Writing that wish down is useful, but it does not make it true.

What is “observed state”?

It is what a tool reports from one place at one time. For example, a browser records a failed request, or a command shows a running process. Every observation has limits: the tool may not see another layer.

Verification means matching evidence to the promise. If the promise is “a user can summarize a document,” useful verification should exercise the real route from the user action to a displayed result, in the target environment, using a known version.

Part 5 · Why the six controls exist

AI can help with the work. Someone must still control the outcome.

A control is a deliberate guardrail or check that keeps a change within known boundaries. Think of a seat belt: it does not drive the car, but it protects against a class of harm. In engineering, a control is a question we insist on answering, a check we insist on running, or a safe limit we insist on preserving.

Let’s be precise about AI. AI can help gather context, review code, write tests, inspect logs, draft a rollback plan, and summarize an incident. The point is not that AI can never perform these tasks. The point is that a team must explicitly define the boundaries, decide what evidence is sufficient, authorize risky actions, and remain accountable for consequences. Never treat “the AI did it” as evidence that these responsibilities were satisfied.
01

Context

Understand the situation before changing it.

First-principles question: What facts must be true for a proposed fix to be right here?

Code is not executed in a vacuum. It runs with a particular browser address, server address, software version, identity, permissions, data, and environment. A fix that assumes the wrong setting can be perfectly reasonable and still fail—or create a security problem.

  • What outcome was requested, and how will success look?
  • Which environment and exact version are involved?
  • Which component calls which other component?
  • What constraints matter: privacy, permissions, cost, compatibility, or downtime?
AI can help

Summarize repository files, infer dependencies, list missing facts, or ask clarifying questions.

Evidence/output

A written requirement, environment facts, request-path sketch, and assumptions marked as assumptions.

02

Review

Understand the proposed change before accepting it.

First-principles question: What will this change cause the system to do differently?

A patch is a proposal. Reviewing means comparing the old and new behavior, not merely checking whether the code looks polished. A small edit may affect permissions, data handling, network access, performance, or another component.

  • Which files and settings changed?
  • Does the change match the requirement—or solve a different problem?
  • Does it expose secrets, grant extra permissions, or weaken a security boundary?
  • What else might this change break?
AI can help

Explain a diff, identify risky patterns, and suggest focused tests.

Evidence/output

A reviewed change set, understood trade-offs, and explicit acceptance of remaining risks.

03

Verification

Check the property we actually care about.

First-principles question: What observation would convince us the requirement is met?

Every check has a scope. A code parser can tell you whether syntax is valid. A unit test can check one function. A build can check whether files can be produced. None automatically proves the full user journey succeeds. Choose checks that match the claim you intend to make.

  • Write success criteria before running the test.
  • Test both expected success and meaningful failure.
  • Check the right environment and exact version.
  • Keep the actual result, not just “passed” in a chat message.
AI can help

Generate tests, propose edge cases, and interpret test output.

Evidence/output

Repeatable results tied to a version and to the written acceptance criteria.

04

Operation

Observe what happens after the change is running.

First-principles question: What is the real system doing now, not what do we hope it is doing?

After deployment, the system has a live state. It may differ from the configuration we requested. Operation means checking behavior over time and at the boundaries that matter: user requests, service health, errors, latency, and dependencies.

  • Is the expected version actually serving requests?
  • Can the real caller reach the right endpoint?
  • Are errors increasing or users failing?
  • Do logs and metrics describe the same time window as the incident?
AI can help

Correlate timestamps, summarize logs, or spot unusual patterns in metrics.

Evidence/output

Time-stamped observations from the relevant system boundaries, plus known blind spots.

05

Recovery

Know how to reduce harm if the change fails.

First-principles question: If this goes wrong, what is the safest way to restore an acceptable state?

A repair can have consequences too. Reverting code may not reverse a database change. Restarting a service may briefly interrupt users. Disabling a feature may be safer than changing several unknown things at once. Plan recovery while the system is calm—not during an incident when everyone is guessing.

  • What is the known-good version or safe fallback?
  • Can the change be reversed without losing or corrupting data?
  • Who is authorized to perform the recovery?
  • How will we verify that recovery worked?
AI can help

Draft runbooks, identify dependencies, and explain rollback risks.

Evidence/output

A rehearsable recovery procedure, known-good target, and verification step.

06

Learning

Use the incident to reduce the chance of repetition.

First-principles question: What did the system teach us, and what will we change because of it?

If a team only restores service, the same hidden condition may trigger the same failure next week. Learning means preserving facts—what users saw, what was observed, which hypotheses were ruled out, what fixed it, and what could prevent recurrence. It is not a search for someone to blame.

  • Record a timeline with timestamps and versions.
  • Separate observed facts from assumptions.
  • Identify the contributing conditions, not just the final symptom.
  • Turn the lesson into a test, alert, runbook, or safer default.
AI can help

Build a timeline, draft a post-incident review, and suggest preventative tests.

Evidence/output

A factual incident record and tracked prevention work with an owner.

The six controls are connected—not six magic words.

They form a continuous loop. Context helps us choose a change. Review asks whether the proposal is sound. Verification tests the promise. Operation checks the live system. Recovery limits harm when things go wrong. Learning improves the next change. A team may automate parts of this loop; it must not leave the loop ownerless.

Part 6 · Worked example from first principles

One line of code. One very important question: “Whose localhost?”

The generated frontend patch includes this line:

const API_BASE_URL = "http://localhost:8000";

It looks plausible. The developer says, “The API works on my laptop on port 8000.” But the frontend code runs inside the user’s browser. To reason correctly, we need to unpack four concepts.

Concept 1

What is an address?

An address tells a program where it should try to contact another program. A URL such as http://localhost:8000 contains a scheme (http), a host name (localhost), and a port number (8000).

Why a port? One computer can run many network services. A port is like a numbered entrance that helps the computer route incoming traffic to the intended service.

Concept 2

What does localhost mean?

localhost means “this same computer or network environment from the point of view of the program making the connection.” It does not mean “the computer where my backend happens to live.”

If JavaScript in a customer’s browser asks for localhost:8000, it tries to contact port 8000 on the customer’s own device—not automatically the developer’s laptop or cloud server.

Concept 3

What is a browser origin?

A web page has an origin, defined by its scheme, host, and port. For example, https://app.example.com is a different origin from http://localhost:8000. Different origins matter because browsers enforce security rules around which scripts can read responses from which sites.

Concept 4

What is CORS?

CORS stands for Cross-Origin Resource Sharing. It is a browser-enforced mechanism in which a server uses response headers to say which other website origins may read certain responses. It is not a generic “network is broken” setting and should not be disabled as a shortcut.

The key deduction: The line may be correct for local development and wrong after deployment. The spelling and syntax can be valid while the destination is wrong for the environment.

Follow the reasoning rather than guessing

State the requirement

When a user clicks “Summarize document” in the deployed app, the browser must reach the intended API address and the screen must show the result or an understandable failure.

Identify who makes the connection

The JavaScript fetch call is made by the browser. Therefore we must interpret the address from the browser’s point of view, not from the developer’s terminal.

Observe the actual request

Open the browser’s developer tools and select the Network panel. This panel records requests made by the page. Click the button once and inspect the request URL, method, response status if available, and any browser error.

Interpret the result carefully

No request in the panel may point to code that never initiated the request or to a filter/recording issue. A failed request can indicate a network problem, a blocked cross-origin response, a server error, or a wrong URL. The exact error matters.

Check the right boundary next

If the request URL is wrong, inspect environment configuration and how the frontend build receives it. If the URL is right but cannot connect, test reachability and server listening. If a response exists but is rejected by the browser, inspect CORS headers and the browser console. If the server returns an error, inspect the backend’s response and logs.

Repeat after the repair

Use the same user action in the intended environment and confirm the deployed version returns the expected result. Keep the observed evidence with the version you checked.

Important distinction: An API URL is usually configuration, not a password. But in a frontend build tool such as Vite, variables exposed to client code with the VITE_ prefix are included in the browser bundle. Do not put secret credentials there; users can inspect code delivered to their browsers.

Part 7 · From symptom to diagnosis

Choose observations that separate possible causes.

A diagnosis is not simply a story that sounds plausible. It is an explanation supported by observations, after checking alternatives. Suppose the home page loads, the backend process appears to be running, and the button says “Could not fetch status.” We do not yet know which boundary failed.

Intervention

An intervention changes the system: restart a service, increase a timeout, rebuild an image, or change a setting. Sometimes interventions are necessary, but doing one before observing may hide the evidence that would have explained the fault.

Observation

An observation gathers information without deliberately changing the system: inspecting the request URL, status code, browser console, service logs, or current version. The best next observation depends on what is still unknown.

1. Describe the symptom exactly

Record the action, the visible message, time, user/environment, and version if known. “It is broken” is too vague to compare against evidence.

2. List possible explanations

For example: wrong address, service not reachable, browser blocked access, backend returned an error, or frontend failed to parse the reply. These are hypotheses, not facts.

3. Pick a discriminating observation

A discriminating observation helps distinguish between explanations. Inspecting the browser request tells us whether the browser tried a URL and what it saw; it is more informative than immediately rebuilding everything.

4. Change one thing at a time when safe

After evidence points to a likely cause, make a proportionate change. If you change address, timeout, service state, and deployment all at once, you may not learn which change mattered.

5. Verify the outcome and record it

Repeat the original user action. Confirm that expected behavior now occurs and that the fix did not violate a security, data, or reliability constraint.

Evidence-first is not “never act.” It means gather enough information to choose a safe next action. In an urgent incident, the first move may be a pre-approved safety action; record the evidence you can and verify recovery immediately afterward.

Part 8 · The operating contract

Eight questions before declaring a change done.

This checklist is not paperwork for its own sake. Each question exists because a specific kind of failure is possible. Open each one to see its purpose and the evidence that answers it.

01 · What user or business outcome is required?

Start with the behavior the person should experience, not the command you plan to run. Without this, a team can successfully deliver the wrong thing.

Evidence: a testable acceptance criterion, such as “the deployed button displays a summary for an authorized document.”
02 · Which components and boundaries change?

Find every part touched by the request. A frontend configuration change may affect the browser-to-API connection even if backend code did not change.

Evidence: a simple request-path sketch and a list of affected components.
03 · Which exact version is intended?

Names like “latest” can point to different things at different times. When a report says “the new version is broken,” you need to identify which new version is actually in use.

Evidence: commit identifier, build/release number, or image digest appropriate to the system.
04 · Which permissions and secrets are needed?

Permissions describe what an identity is allowed to do. A secret is sensitive information such as a password or private API credential. Giving more access than necessary or placing a secret in browser code can create real harm.

Evidence: reviewed permission changes and confirmation that private credentials are not exposed in source or client-delivered files.
05 · What does healthy behavior look like?

“Healthy” must mean something observable. A service process existing is not enough if the real request fails or the result is wrong.

Evidence: expected request, response content/status, screen behavior, and any meaningful performance or error threshold.
06 · Which observations distinguish likely failures?

Plan which signal you will inspect if the outcome fails. This avoids randomly restarting components and hoping one of the changes helps.

Evidence: an investigation path linking each major hypothesis to a useful observation.
07 · What is the safe recovery path?

Decide how to limit harm if the change causes trouble. A code rollback may not undo data changes, so recovery needs to consider what the change actually touched.

Evidence: known-good version, safe disable/rollback steps, data implications, and an assigned decision-maker.
08 · How will the result be verified and recorded?

A successful command is not the finish line. Check the required outcome in the intended environment and keep enough facts for someone else to understand what happened.

Evidence: before/after observations tied to the deployed version, timestamp, and acceptance criterion.

Part 9 · At production scale

One laptop forgives. A fleet multiplies every gap.

Everything so far was explained with one browser, one API, and one developer. Real production systems run the same software on hundreds or thousands of machines, in several regions, changed by many teams many times a day. The six controls do not change at scale—but the cost of skipping one grows with the number of machines, users, and changes it touches. Each card below is a failure mode that only appears, or only becomes dangerous, at scale.

Failure mode · Global blast radius

A change that reaches everything at once

Mechanism: Configuration and rules often propagate to every server within seconds, faster than any human can watch. On 2 July 2019, Cloudflare deployed a single new firewall rule whose regular expression caused excessive backtracking; it was pushed globally in one step and drove CPU to exhaustion on machines handling HTTP traffic across its network.

What operators see: errors rising in every region at the same moment, aligned to a deployment timestamp—not a gradual, local problem.

Production control: progressive delivery. Release to a small canary first, compare its error and latency signals with the rest of the fleet, then widen in stages. Treat configuration as a change that deserves the same staged rollout as code.

Failure mode · Partial truth across a fleet

“I tested it” means one instance answered

Mechanism: Behind a load balancer, your request reaches one of many instances. During a rollout some instances run the old version and some run the new one. A successful manual check proves only that the instance you happened to reach behaved correctly at that moment.

What operators see: a small, persistent error percentage—often reported as “intermittent”—that matches the fraction of instances on the bad version or in the bad zone.

Production control: label every metric, log, and trace with version, region, and instance. Compare cohorts (new versus old) instead of looking at one global average that hides a broken minority.

Failure mode · Recovery depends on what broke

The repair tools sit behind the outage

Mechanism: On 4 October 2021, a command issued during routine maintenance unintentionally disconnected Facebook’s backbone network. Its DNS servers then withdrew their route announcements, making the services unreachable—and the outage also disabled internal tools engineers would normally use to investigate and recover, slowing the response.

What operators see: everything is down, and the dashboards, chat, and remote access they would use to diagnose it are down too.

Production control: design and rehearse an out-of-band recovery path that does not depend on the system being recovered. A rollback plan you cannot reach during the failure is not a recovery control.

Failure mode · A correct procedure, a wrong input

An authorized human, an established playbook, a typo

Mechanism: On 28 February 2017, during an S3 debugging task in AWS’s US-EAST-1 region, an authorized engineer ran a command from an established playbook to remove a small number of servers. One input was entered incorrectly and a much larger set was removed, including servers supporting subsystems that other S3 functions depended on. Restarting those subsystems at their grown size took longer than expected.

What operators see: a dependency that many other services silently relied on fails, and the failure spreads far beyond the original component.

Production control: move the safety check into the tool. AWS reported changing the tool to remove capacity more slowly and to refuse removals below a subsystem’s minimum capacity. A rule the tool enforces is stronger than one a tired person must remember.

Scale changes the review problem too. AI-assisted development increases how many changes a team can propose, but human review attention does not grow at the same rate. If reviewers start approving by volume, Review silently degrades into a rubber stamp. At scale the answer is not “review harder”; it is to encode evidence requirements as automated, version-tied checks, and to spend human judgment on risk, boundaries, permissions, and recovery.

Part 10 · Practice the reasoning

Do not memorize the slogan. Make the next decision.

Choose an answer before opening the explanation. The goal is not to guess what the author wants; it is to reason from the evidence you have.

Scenario 1 · A build succeeds

The automated pipeline is green. No test in that pipeline opened the deployed app or clicked “Summarize document.” What can you conclude?

Reasoning: A successful check is useful evidence for the thing it checked. It is not evidence for every property that was not tested. This avoids both extremes: trusting a green build too much and dismissing it entirely.

Scenario 2 · The browser calls localhost

The API is running on the developer’s laptop. The deployed frontend sends requests to http://localhost:8000. What is the first concern?

Reasoning: The browser is the caller. “Localhost” is interpreted from the caller’s environment. Inspect the actual request and environment-specific configuration before assuming CORS or any other specific cause.

Scenario 3 · The feature fails and you have no diagnosis

The page loads, the API process appears to be running, but clicking the button fails. Which next step is most useful before changing the system?

Reasoning: The browser request observation helps identify which boundary to investigate next. It does not guarantee the cause, but it narrows the possibilities without first changing several variables.

Reference · Plain-English glossary

Technical words, without the assumed knowledge.

Use this section whenever a word feels like jargon. Search by a term or a phrase. You do not need to memorize the glossary; learn to ask what each word means in the current situation.

25 terms
Acceptance criterion

A specific, observable condition that must be true for work to count as successful. “Users can get a summary” is a goal; a precise criterion states the expected action and result in a way that can be checked.

API

Application Programming Interface: an agreed way for one program to ask another program for something. The agreement can define the address, request format, authentication, and reply format.

Artifact

A produced item that can be inspected or passed to another stage, such as a compiled package, static website files, a container image, or a release bundle.

Backend / server

The program or system that handles work behind the visible screen. “Server” can mean the computer, the software process, or the role of responding to requests, so check the context.

Browser / client

The application on the caller’s side, such as Chrome. In a web app it displays the interface and runs client-side code. “Client” more generally means the side making a request.

Build

A process that turns source files and dependencies into output that can be run or deployed. A successful build says that process completed according to its checks; it does not prove all runtime behavior is correct.

CI / pipeline

CI means Continuous Integration: automated work that checks code changes. A pipeline is a sequence of jobs, often including tests, analysis, packaging, and deployment. Its value depends on what the jobs actually check.

Commit / Git

Git records versions of files. A commit is a named snapshot of changes. A commit identifier helps people discuss exactly which version they mean.

Configuration

Settings that influence how software behaves without necessarily changing its core code—for example, the API address to contact or the log detail to emit.

CORS

Cross-Origin Resource Sharing: a browser security mechanism using HTTP response headers to control whether scripts from one origin may read responses from another origin. It is not a password and not a universal fix for connectivity problems.

Deployment

The process of putting a version of software or its configuration into a target environment. A deployment operation reporting success does not automatically prove the user-facing behavior is correct.

Developer tools / Network panel

Built-in browser tools that help inspect page behavior. The Network panel records network requests and responses, such as the destination URL, method, status, and timing.

Endpoint

A particular address and operation through which a service can be reached—for example, a route used to ask for a document summary.

Environment

The conditions and place in which software runs. Development, testing, staging, and production often have different addresses, credentials, data, permissions, and scale.

Frontend / user interface

The portion a person sees and interacts with: buttons, fields, text, menus, and visible state. The frontend may run in the browser and may call backend services.

HTTP request / response

HTTP is a common web communication protocol. A request asks for something and can include a method, address, headers, and data. A response returns a status and may include headers and a body.

HTTP status code

A number summarizing how the server handled an HTTP request. For example, 200 commonly means success, 404 means the requested resource was not found, and 500 indicates a server-side error. The status alone may not prove the business result is correct.

localhost

A special host name referring back to the local computer/network environment from the program making the connection. A browser on a customer’s device does not use localhost to reach a developer’s laptop.

Log

A record written by software about an event, often with time and details. Logs can help explain what happened, but missing logs are not conclusive proof that an event did not happen: logging may be absent, filtered, delayed, or stored elsewhere.

Port

A numbered network endpoint that helps a computer direct incoming traffic to the right listening program. Many programs can share a computer by using different ports.

Process

A running instance of a program. A process existing does not guarantee that it is ready, reachable, configured correctly, or producing correct results.

Production

The live environment that real users, customers, or business operations rely on. Changes there can affect real work and data, so stronger checks and recovery plans are needed.

Rollback / recovery

A way to return a system to an acceptable state after a change causes trouble. Reverting code may not reverse data changes or external side effects, so recovery must match the change.

Secret / credential

Sensitive information used to prove identity or grant access, such as a password, private token, or API key. Browser-delivered code can be inspected by its users, so it must not contain private credentials.

Telemetry / monitoring

Signals collected from a running system. Logs record events, metrics record numerical measurements over time, and traces show how one operation travels across components. These signals support diagnosis but each has blind spots.

The lesson in one sentence: Generated code is a proposal; reliable engineering is the practice of defining the outcome, understanding the change, gathering matching evidence, observing the live system, recovering safely, and learning from what happens.

Mapped model and its limits

A recipe maps to an artifact; an order specifying a meal and table maps to intended state; “the oven is on” maps to one observed fact; the correct meal reaching the customer maps to a verified outcome. A printed recipe does not prove delivery. Software can cache, retry and serve many callers at once; this analogy does not implement browser policy. Return to the actual caller, address, response and rendered result.

Complete illustrative trace

Assume browser and API share one laptop, port 8000 has the API listener, and the origin is allowed. The page loads, its click resolves localhost on that laptop, the API returns a response, and the browser reads and renders it. Now move only the browser to a second laptop with no listener on port 8000. The same address points at that second laptop, not the developer's API. The page may load while its action fails. A corrected reachable API address is only a proposed fix until a repeated click returns the intended response and screen result from that caller. No run is claimed here.

Transfer and lab handoff

A mobile order says “accepted,” but the customer has no receipt. Separate artifact, intention, observation and required outcome without assuming CORS is involved. Predict what checking the order service versus the customer's screen could establish.
