Part 1 · Begin with the real-world promise

“The page loads” and “the feature works” are different claims.

You open the Week 1 app at http://127.0.0.1:5173. The heading, the layout, and a Check API button all appear. You click the button. The status card says it cannot fetch the status. Nothing on the screen tells you which part of the system failed. This lesson is about finding that part with evidence.

The promise

What the person expects

“When I click Check API, the app asks the backend for its status and shows me the answer—or tells me clearly that it could not get one.” The user does not care which server delivered which file. They care whether the card shows a true answer.

The engineering question

What must be true?

The browser must have loaded the app. The click handler must send a request to the right scheme, host, port, and path. A process must be listening there. It must route the request and return a status, headers, and a body. The browser must be allowed to let the page read the reply. React must read it correctly and update the card.

First principle: one visible symptom (“can’t fetch”) can come from several different boundaries. A boundary is a point where work passes from one program, machine, or policy to another. Diagnosis means finding the first boundary where what you observe differs from what you expected.

The mystery has three independent boundaries

Before we walk the request step by step, see the shape of the problem. The page you see and the data it asks for travel on separate requests, to separate servers, under separate rules.

Boundary A

Frontend asset load

The browser asks the Vite dev server for /. Vite returns HTML that references JavaScript and CSS files; the browser downloads and runs them, and React draws the interface inside the page’s root element. This request goes to port 5173.

Boundary B

Browser → API fetch

After the click, JavaScript running in the page calls fetch() against a separate host and port—here http://127.0.0.1:8000/api/status. It is a brand-new HTTP request to a different program. Success at Boundary A says nothing about it.

Boundary C

Response + browser policy

A reply has a status, headers, and a body. Before page code may read a cross-origin reply, the browser checks CORS headers. Then React must check the status and parse the body. Each of these is a separate pass/fail check.

Two easy over-claims to unlearn right now. A React screen loading successfully is not evidence the API is reachable—the screen came from Vite, not FastAPI. And FastAPI’s own /docs page working in a browser tab is not evidence that the app’s page can read API responses: opening /docs is a same-origin visit to port 8000, while the app’s fetch is a cross-origin call from port 5173 with its own requirements.

Build the vocabulary from everyday language

These words appear on every screen of this lesson. Learn the short meaning here; the glossary gives fuller definitions.

HTTP request / response

HTTP is the message format browsers and servers use. A request names a method (such as GET), a path, and headers. A response carries a status code (such as 200 or 404), headers, and often a body.

Scheme, host, port, path

The four parts of a URL that decide where a request goes. In http://127.0.0.1:8000/api/status the scheme is http, the host is 127.0.0.1, the port is 8000, and the path is /api/status.

Port

A number that lets one machine run many network programs. The operating system delivers a connection for port 8000 to whichever process is listening on 8000. If nothing listens, the connection is refused.

Origin

The combination of scheme, host, and port of a page. http://127.0.0.1:5173 and http://127.0.0.1:8000 are different origins because their ports differ. Browsers apply security rules per origin.

Vite dev server

A development program that serves your frontend source files to the browser and rebuilds them as you edit. In Week 1 it listens on port 5173, Vite’s default.

FastAPI / uvicorn

FastAPI is a Python framework for writing API routes. It runs inside an ASGI server, usually uvicorn, which owns the network listener—by default 127.0.0.1:8000—and hands each request to FastAPI.

Part 2 · Derive the architecture

Six steps from the click to the rendered card.

The full journey has two request/response exchanges and several checks between them. Select each step to see what happens, what a success at that step proves, and—just as important—what it does not prove. Each step is a separate place the journey can stop.

Step 1 · Frontend load

The browser loads the frontend

The learner navigates to http://127.0.0.1:5173. The Vite dev server returns an HTML document that references JavaScript and CSS. The browser downloads and executes the JavaScript, and React builds the user interface inside the page root element.

Example: Proves: the frontend server served enough assets for the browser to render the page. Does not prove: that the API server is running, that the API URL is correct, or that a later API request will succeed.

The same journey as a message sequence

Read top to bottom. The browser talks to two different servers and performs a read-policy check distinct from server handling. This is an illustrative sequence, not captured traffic.

User → Browser: open http://127.0.0.1:5173
Browser → Vite: GET / (HTML, then JS and CSS files)
Vite → Browser: 200 OK + HTML / JavaScript / CSS
Browser: execute JavaScript, React renders the page
User → Browser: click "Check API"
Browser → API: GET /api/status (with Origin: http://127.0.0.1:5173)
API: uvicorn accepts; middleware wraps FastAPI routing and response
API → Browser: HTTP status + headers + JSON body
Browser: apply CORS policy, then hand the response to page code
React → User: show the status message, or an actionable error

Why the request target is spelled out

The default target is http://127.0.0.1:8000/api/status; configuration can override its base URL. Each part is a fault boundary. A wrong scheme can cause TLS or mixed-content failures; loopback has special browser security treatment, so inspect the actual error. A wrong host points elsewhere. A wrong port may have no listener or another service. A wrong path may return 404 from a reachable server. Later modules examine deployed configuration.

Why two servers instead of one

Vite serves and transforms frontend files during development. FastAPI handles Python API operations inside Uvicorn, the listener-owning server. ASGI is their request-handling interface. Two processes on different ports create a cross-origin boundary. If the page and API shared an origin, CORS permission would not be needed for that read; this would not remove authentication requirements.

What the API actually returns

FastAPI maps method and path to a Python function, called a path operation. Here its dictionary becomes JSON: named fields with values. The supplied GET /api/status handler returns these exact values:

{
  "service": "groundops-api",
  "status": "available",
  "message": "The browser reached the FastAPI endpoint.",
  "version": "0.1.0"
}

Service names the app; status is declared status text; message is display text; version is an application label, not a unique source revision. The fixed message says “browser” even when curl calls the route. It does not identify the caller or prove a browser run. We make no production capacity, authentication or availability guarantee.

Keep this mental picture: the six steps expose independent failure boundaries. Success at an earlier step does not automatically establish a later one; choose evidence matching the claim.

Part 3 · The incident and its instruments

Six instruments. Six different scopes.

Here is the incident. The page renders. The Check API button produces “Could not fetch status.” A teammate says, “the API is fine, I just curled it.” Someone else says, “restart everything.” Neither statement is a diagnosis yet. To find the boundary, you need instruments—and you need to know exactly what each one can see.

First, decode the tools you will use:

DevTools

Developer tools built into the browser (open with F12, or Cmd+Option+I on a Mac). They show what the browser itself did: requests sent, responses received, and errors raised.

Network panel

The DevTools tab that records every request the page makes, with its URL, method, status, timing, request and response headers, and body where available. It only records while DevTools is open.

Console panel

The DevTools tab that shows JavaScript errors and browser messages—including the CORS explanation that page code itself is not allowed to see.

curl

A command-line HTTP client. curl -i URL sends a request and prints the status line and response headers (-i means “include headers”) before the body. It is not a browser and enforces no CORS policy.

Server terminal / log

The terminal where uvicorn runs prints a line for each request it handles and a traceback for unhandled exceptions—at the configured log level only.

Source and config

The files that declare intent: the API URL constant or VITE_ variable in the frontend, the CORS origin allowlist and route declarations in the backend.

Open each instrument: what does it support, and what can it not prove alone?

Select every card. The label tells you the instrument; the hidden line tells you the limit of its scope.

0 of 6 opened. Select every instrument card. Notice that no single instrument can tell you where the request stopped on its own.

Important reasoning rule: every instrument observes from one position at one moment. Before you trust a reading, ask: who made this request, from where, to which URL, and what is this tool able to see? “I curled it and it worked” answers a question about your terminal, not about the user’s browser.

How each instrument works inside

Inside the Network panel

A recorder, not a probe

The Network panel does not send anything itself. It records the requests the page makes while DevTools is open, so you must open it before clicking. An empty list can mean the code never called fetch, the request was filtered out by the panel’s filters, or recording started too late. Chrome shows a blocked cross-origin request with the status CORS error and a refused connection as (failed) with net::ERR_CONNECTION_REFUSED.

Inside curl

A different caller in a different place

curl resolves the host name, opens a TCP connection, sends the request, and prints what comes back. It runs wherever your shell runs: your laptop, a container, or a remote VM over SSH. That makes it an excellent test of “can this location reach the server?” and a poor test of “can the user’s browser read the reply?”—curl sends no Origin header unless you add one, and never blocks a response for CORS reasons.

Inside the server log

Evidence written by the process itself

uvicorn prints an access line such as INFO: 127.0.0.1:54321 - "GET /api/status HTTP/1.1" 200 OK after it handles a request. The line proves the request reached this process. Its absence is weaker: access logging may be disabled or set to a higher log level, output may go to another terminal, or the request may have gone to a different process entirely.

Inside config files

Intended state, not observed state

A config file is what you asked for. The running process uses what it loaded when it started. Vite reads .env files at startup and replaces import.meta.env.VITE_* references in client code, so editing .env without restarting the dev server leaves the old value in effect. FastAPI’s CORS middleware is configured when the app object is created, so allowlist changes need an API restart too.

Combine signals from both sides. Google’s SRE book recommends combining external symptom signals with internal cause signals, especially in layered systems. A slow or failing request is a symptom for the frontend owner and a clue about a dependency for the API owner. The browser instruments show the symptom; the server instruments show the cause.

Part 4 · Three failures that look alike

Same user-visible message. Three different failure boundaries.

These controlled lab cases can all reach the page's Request failed state. Compare their actual destinations, listener evidence and browser permissions, not just the error wording. Select each case and then the healthy baseline.

Failure A · Wrong API target

Wrong API target

Network shows the browser's actual URL differs from the intended API URL; a direct check of the intended route succeeds. Correct only the supported configuration mismatch, reload it as required, then repeat both direct and browser checks.

Example: no API log alone does not prove no arrival; check logging coverage, target and time.
A · Wrong API target

First divergence: request URL

Evidence: the browser targets port 8001 while the intended route answers at 8000. With no listener at 8001, the connection fails.

Correction: fix the effective base URL, restart Vite when needed, reload and verify the original action. If another service answers on the wrong port, save that different result rather than calling it the intended experiment.

B · Stopped API

First divergence: listener

Evidence: the intended target remains correct, the process is stopped and the direct request cannot connect. A timeout alone does not prove the process stopped; it needs corroboration.

Correction: restore the API under the lab procedure and verify health, route and browser. Outside the deliberate experiment, investigate why it stopped rather than naming restart as the cause.

C · Disallowed browser origin

First divergence: read policy

Evidence: this simple GET can arrive and return 200, but the response has no allow-origin header for the actual page origin. Console provides the policy diagnostic; curl may print the body.

Correction: restore the smallest intended allowlist, restart the API and repeat from the original page origin. Do not disable browser security or treat CORS as authentication.

Why the page message is insufficient

Connection failures and CORS failures can both reject fetch with a generic TypeError. Page code does not receive the detailed CORS failure explanation; use Console and corresponding network/server evidence. This does not mean browsers reveal no information through any possible side channel, nor that every fetch rejection has the same cause.

Origin is a parsed tuple, not the whole typed URL

For these HTTP(S) pages, origin is the normalized scheme, host and effective port. URL parsing handles case and default ports; paths are excluded. Localhost and 127.0.0.1 remain distinct hosts even if both reach the same machine. They are not guaranteed to reach the same listener because IPv4/IPv6 resolution may differ. Use the actual browser origin when comparing the allowlist, and keep the caller fixed during the policy experiment.

The symptom is not the cause. These cases isolate one changed condition for teaching. Real incidents can combine faults. Find a supported divergence, test alternatives and repeat the failed outcome after a targeted correction.

Part 5 · The disciplines of tracing

Four habits turn instruments into a diagnosis.

Instruments only help if you use them in a disciplined way. Each habit below exists because a specific mistake is common: trusting the wrong caller, testing from the wrong place, reading silence as proof, or trusting a file over the running process.

01

Observe the browser’s request

The browser is the caller. Start where it starts.

First-principles question: What exactly did the browser try to do, and what did it record?

The browser decides the final URL, adds the Origin header, and applies CORS. No other tool can see those decisions. Open DevTools before reproducing so the Network panel records the attempt.

  • Open DevTools → Network, clear it, and click Check API exactly once.
  • Record the full request URL, method, status (or (failed) / CORS error), and timing.
  • Check the Console for the browser’s own explanation.
  • If no request appears, check filters and whether the click handler ran at all.
Supports

Whether a request was attempted, to which URL, and the browser-level outcome.

Cannot prove alone

Why the server behaved as it did.

02

Test the API directly

Take the browser out to isolate the server.

First-principles question: If I remove the browser, the page code, and CORS, does the server answer?

curl -i tests the listener, routing, and response with nothing in between. Adding -H "Origin: http://127.0.0.1:5173" lets you see which CORS headers the server would send to that origin—without the browser enforcing them.

  • Run curl against the expected URL, then against the actual URL from Network.
  • Read the status line, the headers, and the body.
  • Note where the shell runs: your laptop, a container, or a VM.
  • Compare connection refused, timeout, 404, and 500—they mean different things.
Supports

Reachability and HTTP behaviour from that command’s location.

Cannot prove alone

Browser CORS enforcement, the browser’s network path, or React rendering.

03

Read the server’s own evidence

Let the process tell you what it received.

First-principles question: Did the request arrive at this process, and what did the process do with it?

A log line written by the server is evidence from inside the boundary. It confirms arrival, method, path, and status. A traceback shows where Python code failed. But logs are only as complete as their configuration.

  • Find the terminal running uvicorn and confirm it is the process on the expected port.
  • Match the log line to your click by time, method, and path.
  • For a 500, read the traceback; it names the failing line.
  • Before reading silence as “no traffic,” confirm access logging is on.
Supports

Arrival and handling inside the API process.

Cannot prove alone

Unlogged requests, or anything the browser did after the reply left.

04

Compare intended vs effective config

The file says what you meant. The process does what it loaded.

First-principles question: Is the running process actually using the configuration I am reading?

Configuration flows from files and environment variables into a process at a specific moment—usually startup or build time. Any change after that moment is invisible to the running process until it restarts or rebuilds.

  • Compare the URL in source/.env with the URL in the Network panel.
  • Compare the CORS allowlist with the Access-Control-Allow-Origin header curl shows.
  • Check for environment-variable overrides and multiple .env files.
  • When they differ, restart the right process and observe again.
Supports

What the system was told to do.

Cannot prove alone

What the running system is doing now.

Part 6 · Worked example from first principles

One click, twelve fields, no guessing.

Record expectation beside observation, then test explanations against alternatives. This is an illustrative worked trace of Failure C, not recorded execution. Assume one laptop, no proxy, the supplied handler, and a simple GET without credentials or custom headers.

Concept 1

Expected vs actual

The expected API URL comes from the requirement/configuration. The actual URL comes from the browser. A difference locates a boundary; matching values do not prove all later steps work.

Concept 2

First divergence

Find the first observed mismatch. Later failures may be consequences or additional faults; do not assume there can be only one cause.

Concept 3

Hypothesis, not conclusion

“The API does not allow http://127.0.0.1:5173” predicts no matching Access-Control-Allow-Origin on this response. Write that prediction before inspecting headers.

Concept 4

Falsifying test

If a direct response has the matching header, the simple allowlist explanation is insufficient. Compare the browser's actual response and request mode; proxies, caches and credentials can make requests differ. Surviving one test alone does not establish a root cause.

Worked trace: change only the allowed origin

Baseline: with http://127.0.0.1:5173 allowed, the API returns 200, the matching header and the supplied JSON; the browser reads it and renders Response received. Now allow only http://localhost:5173 and restart the API. Keep the page at 127.0.0.1. Predict separately: will curl obtain a response, and will page code be allowed to read it?

Record the page and its origin

Address bar: http://127.0.0.1:5173/. Origin: http://127.0.0.1:5173, the scheme/host/effective-port tuple, without a path.

Record the expected target

GET http://127.0.0.1:8000/api/status. The listener and route are unchanged.

Reproduce with DevTools open

Network shows the intended URL and a blocked cross-origin read. Console explains the missing permission. This plain GET can reach the server without an OPTIONS preflight.

Compare a direct request with the actual Origin

Curl with Origin: http://127.0.0.1:5173 returns 200 and JSON, but Access-Control-Allow-Origin is absent. The supplied restrictive middleware omits the header for a disallowed origin; it does not send the other allowed origin instead.

Correlate the server log

A matching GET /api/status HTTP/1.1" 200 OK supports arrival and route handling for that request. It does not prove browser readability. Curl also creates a log entry, so match the single click by time and order.

Test the explanation without moving the caller

Compare the effective API allowlist with the actual Origin and missing response header. Keep the frontend hostname fixed: switching to localhost could also alter IPv4/IPv6 resolution and would no longer isolate the allowlist change.

Restore and verify

Restore the exact intended origin, restart the API and repeat direct and browser checks. The expected after-state is 200 plus a matching allow-origin header, the documented body and Response received. If any is missing, record the contradiction and continue investigating; do not claim the scenario passed.

Part 7 · From symptom to diagnosis

“localhost” follows the caller's network context.

Loopback traffic returns within the caller's network namespace. Different callers can share that namespace or occupy different ones; a different program does not automatically mean a different machine. The following examples assume ordinary isolated container/Pod networking and direct connections unless a forwarding path is explicitly described.

Context A

Browser on a laptop

The page's code executes in the browser, even when a remote server supplied it. A direct request to localhost therefore targets the browser machine's loopback, not automatically the machine that supplied the page.

Limit: a published port, local proxy or tunnel can deliberately forward that connection elsewhere. Inspect whether such a path exists rather than claiming localhost can never reach a container or remote API.

Context B

Isolated Docker container

Ordinary bridge-networked containers have a separate network context. Their localhost is not the host's loopback. A listener bound only to container 127.0.0.1 is not ordinarily reachable through traffic forwarded to the container's network interface.

Consequence: the server needs a reachable container-interface binding, often 0.0.0.0, plus appropriate publication and policy. This is not permission to expose the Week 1 server broadly. Host-network/shared-namespace modes change the model. Docker Desktop's documented host.docker.internal name provides a host-reaching route; service binding and policy still matter.

Context C

Remote shell and an explicit tunnel

Curl in a remote VM shell tests that VM's localhost, not your laptop. A successful result is evidence about that caller and route.

Changed condition: an authorized SSH local forward can deliberately bridge the contexts. In the illustrative syntax ssh -L 8000:localhost:8000 vm, SSH listens locally and opens the destination connection to localhost:8000 from the remote side. This is protocol explanation, not a Week 1 command to run; authentication, binding, available ports and authorization must also hold.

Context D

Ordinary Kubernetes Pod networking

Containers in one Pod share its IP address and port space, so they can communicate using localhost. Different ordinary Pods do not share that loopback and use an appropriate Service or Pod address instead.

Limit: host-networked Pods are a different topology. Do not infer namespace separation merely from two process or Pod names; identify the actual networking mode before predicting reachability.

Address family is another condition. Localhost can resolve to IPv4 127.0.0.1 and IPv6 ::1. Uvicorn's default host is 127.0.0.1 and port is 8000; the lab also supplies these explicitly. With no IPv6 listener, a client attempting only ::1 may fail even when IPv4 works. Compare resolved destination and listener instead of treating every hostname failure as CORS.

Choose observations that separate causes

Intervention

Restarting, editing configuration or rebuilding changes state and can discard useful evidence. Recovery alone does not establish which condition mattered. Preserve inexpensive observations first when safe.

Observation

Read the actual Network result, Console diagnostic, direct response and relevant logs. A discriminating observation has different predicted results under different explanations. Even a diagnostic HTTP request adds load and logs; “read-only” is about intended application effects, not zero side effects.

1. Record the symptom

Name the action, actual message, caller and time. “API down” is an explanation, not a raw observation.

2. List credible explanations

Wrong target, unavailable listener, policy rejection, server error and incorrect response handling predict different evidence. More than one may contribute.

3. Locate the caller

Identify the browser or shell initiating the connection, its network context and any proxy or tunnel. A test from elsewhere answers a different question.

4. Compare the actual request

A wrong URL points toward configuration. Connection refusal concerns connection establishment. A CORS diagnostic concerns browser policy. A 500 is an HTTP server-error response; a 200 still needs body and rendering checks. These are leads, not unique root causes.

5. Cross-check at the other boundary

Compare the corresponding direct response and server log with the same target/time. Missing logs require known coverage, and an intermediary may answer before the API.

6. Correct one supported condition and repeat

Restart only where configuration loading requires it, repeat the original user action and keep before/after evidence. Record any new mismatch instead of extending the old diagnosis to explain everything.

Carry this question forward: which process made the connection, from which network context, through which route? That question—not memorizing a special hostname—makes an unfamiliar topology diagnosable.

Part 8 · The operating contract

Eight claims you must be able to defend.

Before saying “the request works” or “I found the cause,” name the evidence and its limit. Open each question after trying to answer it from your trace.

01 · Did I separate page files from API data?

Vite's page-file exchange and the later FastAPI request are distinct. A rendered page alone does not establish API reachability.

Evidence: document/asset requests and the separate API row, with their actual results.
02 · Do I know each instrument's scope?

Address bar, Network, Console, curl, logs and files see different boundaries. Record caller, location, time and version rather than combining unrelated observations.

Evidence: an instrument attached to each claim, plus a cross-check where its blind spot matters.
03 · Did code check status and body?

fetch() can resolve on 404 or 500. Check response.ok (200–299) or status before treating the body as success; then validate the expected fields. Rejections can include network/policy errors, invalid request inputs or cancellation, not only an unavailable server.

Evidence: defined success and error states, with any unexecuted error tests explicitly recorded.
04 · Did I separate CORS from authentication?

CORS governs cross-origin browser reading, not caller identity or all server access. A simple GET may reach the handler even if the response is unreadable. A JSON POST or non-safelisted header generally requires a preflight, unless a valid preflight result is cached. Curl does not enforce this browser policy.

Evidence: actual Origin, allow-origin response header and any OPTIONS row. The local lab has no authentication; production authorization is a separate requirement.
05 · Did I test look-alike explanations?

Wrong target, stopped listener and disallowed origin can produce similar page errors. A matching URL excludes one mismatch, not every connectivity fault; direct curl and a matching header still do not establish browser rendering.

Evidence: predictions for alternatives, observations from the relevant callers, and contradictions kept in the record.
06 · Did I test where the caller runs?

Localhost refers to the caller's network context. A remote shell, isolated container or Pod can differ from a laptop browser; callers sharing a network namespace share its loopback.

Evidence: the execution context recorded alongside each result.
07 · Is the cause bounded rather than merely plausible?

A tested causal explanation needs more than a hypothesis surviving one check. Compare alternatives and verify a targeted correction; multiple contributing conditions can remain. Recovery does not prove every part of the causal story.

Evidence: discriminating result, relevant change, repeated user action and remaining uncertainty.
08 · Does the failure path fail usefully?

Verify the page action, response and rendered result, then relevant failure behavior. An available response should not become false success, and a failed request should not leave an unexplained spinner. Do not claim unrun failure paths passed.

Evidence: stopped-API recovery in the lab; other HTTP/error-path checks identified separately with their actual execution status.

Part 9 · At production scale

Production can add boundaries the local trace never exercised.

The Week 1 trace has one browser, two processes and one machine. A production design may add DNS resolution, a CDN or proxy, a load balancer, a gateway and downstream services. These are possible topologies, not requirements for every application. Each additional component introduces another place to compare expectation with evidence. DNS lookup is a setup step, not an HTTP request passing through a DNS server.

Failure mode · Preflight cost and stale CORS caches

Two caches can affect one browser request

Mechanism: JSON POSTs and requests with non-safelisted headers such as Authorization or traceparent require preflight permission. An OPTIONS exchange is needed when no applicable cached preflight permission exists. MDN documents a default maximum age of five seconds, Chromium's two-hour cap and Firefox's 24-hour cap; these are browser-version-sensitive limits, not promised retention. FastAPI's middleware default is 600 seconds. A separate shared HTTP cache can reuse one origin's response header for another if its cache policy ignores a varying Origin.

What operators see: an uncached preflight adds a round trip, but not every call pays it and total latency need not double. Different cache states can make users see different behavior. A preflight permission does not remove the browser's checks on the actual response.

Control and cost: a same-origin route removes this cross-origin boundary for those calls, but not authentication needs. Otherwise allowlist intended origins, use Vary: Origin when a cacheable response varies by Origin, and choose cache lifetimes deliberately. Direct checks with an Origin header expose server headers; retain a browser check because curl still cannot enforce browser policy.

Failure mode · Retries without idempotency

“The fetch failed” does not mean “the server did nothing”

Mechanism: a connection can fail after server work finishes; a proxy may time out while work continues; the browser can withhold an already-produced reply. A repeated request may therefore repeat the operation. RFC 9110 defines GET, HEAD, PUT, DELETE, OPTIONS and TRACE as idempotent: their intended effect is unchanged by repetition. POST is not inherently idempotent, although a particular API can provide an idempotency contract.

What operators see: duplicate orders, bursts of retried traffic or a dependency unable to recover under added load. Idempotency concerns intended effects, not identical responses, zero logging side effects or free capacity.

Control and cost: do not automatically retry non-idempotent work without evidence it was not applied or a contract making replay safe. A server-supported request key can deduplicate attempts, but storage, expiration and concurrency semantics must be defined. Bound retries, use capped backoff and jitter, and avoid independent retries at every layer. These are design proposals, not features implemented in the Week 1 app.

Failure mode · Timeouts and tail latency

A slow dependency can dominate one user action

Mechanism: fetch has no numeric timeout option; a supported AbortSignal, such as AbortSignal.timeout(5000), can bound client waiting in milliseconds. That signal uses active time and may pause when a document is suspended; it is not a wall-clock service guarantee. Cancellation does not establish that server work or side effects stopped. An outer proxy can give up before an inner operation completes.

Worked calculation: assume 100 independent calls, each with a 1% chance of exceeding a chosen slow threshold. The chance at least one is slow is 1 − 0.99100 ≈ 63%. Independence and equal probabilities are assumptions; correlated calls or different thresholds change the result. These are illustrative values, not lab measurements.

Control and cost: give the UI an explicit timeout state and propagate a remaining deadline where supported. Reserve time for returning/handling the result instead of letting dependencies outlive the caller's useful budget. Inspect high percentiles and user outcomes alongside averages. An aggressive deadline can reject useful work; choose it from service requirements and observed latency.

Failure mode · An intermediary answers first

The API may not have generated the HTTP response

Mechanism: an edge proxy may terminate TLS and route to an API instance. Gateways can generate their own errors: RFC 9110's 502 concerns an invalid upstream response, 503 temporary unavailability and 504 an upstream timeout. The exact no-healthy-backend behavior is product-specific; some load balancers fail open. No single status proves a particular backend state.

What operators see: a response format unlike the API's, gateway errors and no matching API line, or callers still using cached DNS answers after a change. The missing log alone cannot prove non-arrival.

Control and cost: compare response-producing-layer logs with shared request identifiers, and plan DNS/cache lifetimes before migration. Use representative synthetic user checks separately from instance health decisions. Making every instance fail health because of a shared dependency can remove all capacity; design readiness and fail-open behavior against that risk, not a universal “deep health check” rule.

Failure mode · Partial instance or regional failure

“It works for me” is one caller's sample

Mechanism: a stale setting on one instance can affect only its routed traffic. A manual request might repeatedly reach a healthy instance through affinity or chance, while another cohort fails. This is possible, not a claim that all traffic is evenly balanced.

What operators see: failures correlated with version, location or instance, including an allowlist updated on only part of a fleet. A global average can hide that group.

Control and cost: attach useful version/location identity to appropriate telemetry and compare cohorts. Choose metric dimensions with a cardinality budget rather than attaching every identifier to every metric. External probes from relevant locations extend the evidence population, but remain samples rather than proof of every user's experience.

Failure mode · Losing request identity across services

Trace context joins recorded operations, not missing evidence

Mechanism: W3C traceparent version 00 uses the fields version-trace-id-parent-id-trace-flags, for example 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01. The trace ID is 16 bytes (32 hexadecimal characters); parent-id is an 8-byte identifier for the caller's operation. Instrumentation creates spans with their own span IDs and parent links. When sending a downstream request within that trace, it propagates the trace ID and identifies the sending operation in parent-id.

What operators see: retained spans can reveal relationships and measured durations. The trace ID is a correlation key, not a sortable clock, proof of root cause or guarantee all hops were recorded. Missing instrumentation, sampling and export failures can leave an incomplete trace.

Control and cost: propagate context across intended trust boundaries and correlate logs with spans. Validate untrusted incoming context and avoid sensitive identifiers in headers. Browser-added traceparent is not CORS-safelisted: preflight must permit it (or applicable permission must be cached). Returning an opaque correlation ID can help support, but does not authorize access to private traces.

Scale makes unfounded changes more expensive. Even locally, restarting can lose useful state; no fixed ten-second recovery is promised. A fleet restart can interrupt requests and trigger retries. Observe from the failing caller, keep interventions bounded, and preserve inexpensive evidence without delaying authorized urgent mitigation.

Part 10 · Practice the reasoning

Find the boundary. Then make the claim fit the evidence.

Choose an answer before reading the explanation. Reason from what each instrument can and cannot see.

Scenario 1 · The log is silent

The card fails. The uvicorn terminal shows no line at the time of the click. The Network panel shows a request to http://127.0.0.1:8080/api/status with status (failed). curl to http://127.0.0.1:8000/api/status returns 200. What is the best-supported conclusion?

Reasoning: Network shows the actual target (port 8080) differs from the expected one (8000), and curl to 8000 succeeds, so the API is fine. This is Failure A. The silent log is consistent with the browser calling elsewhere—but on its own it proves nothing, which is why D over-claims.

Scenario 2 · curl works, the browser does not

Network shows the correct URL with status CORS error. The API log shows "GET /api/status HTTP/1.1" 200 OK at the click time. A teammate proposes setting the allowlist to ["*"] and turning on credentials “to be safe.” What is the right response?

Reasoning: The request arrived and succeeded server-side; the browser withheld the reply, so the first divergence is the CORS check. The fix is the smallest correct allowlist. A wildcard cannot be combined with credentials anyway, and CORS is not what protects the API—authentication is. There is no supported way to make page code bypass CORS.

Scenario 3 · The container’s localhost

You move the API into a Docker container and publish port 8000. Inside the container, curl localhost:8000/api/status returns 200. From your laptop’s browser, the card fails with connection refused. uvicorn was started with its default host. What is the most likely first divergence?

Reasoning: The in-container curl tested the container’s own loopback—a different context from the browser. uvicorn’s default host is 127.0.0.1, which inside a container means “only this namespace.” Traffic forwarded through the published port arrives on the container’s network interface, where nothing listens. host.docker.internal is for the opposite direction: a container reaching the host.

Scenario 4 · A 404 that renders as success

After a refactor, the card shows “Status: undefined.” Network shows GET /api/v1/status returning 404 with a small JSON error body. The code does const data = await res.json(); setStatus(data.status). Which statement is correct?

Reasoning: A 404 proves a reachable server answered and had no matching route—here the path changed. fetch() resolves on 404, so the code must check res.ok before treating the body as success. Two fixes: correct the path, and add a real error state so the next failure is visible.

Exit check

Repair this statement.

A learner says: “curl returns HTTP 200, so the frontend is working.” What you know: curl was run from the learner’s own terminal, not the browser; the status card in the UI still shows an error; no one has checked the browser’s Network tab yet. Rewrite the claim so it says exactly what curl proved, and names what is still unverified.

Weak repairs to avoid: “This proves the whole system works, since curl succeeded” (over-claims curl’s scope); “I should restart the frontend, since curl worked but the UI didn’t” (an intervention before an observation); “CORS must be misconfigured, so I’ll allow all origins to be safe” (a guess plus an unsafe shortcut).

“The API route returned HTTP 200 to curl from that command’s environment. I still need to verify the browser calls the expected URL, the response is allowed by browser policy, React handles its status/body, and the requested UI outcome appears.”

Reference · Plain-English glossary

Technical words, without the assumed knowledge.

Use this section whenever a word feels like jargon. Search by a term or a phrase. Learn to ask what each word means from the point of view of the program making the request.

28 terms
Access-Control-Allow-Origin

A response header in which a server names the origin allowed to read the response (or * for any origin, which cannot be combined with credentials). The browser compares it exactly with the page’s origin.

ASGI

Asynchronous Server Gateway Interface: the Python standard that lets a server such as uvicorn hand HTTP requests to an application such as FastAPI. The server owns the network listener; the application owns the routes.

CORS

Cross-Origin Resource Sharing: a browser-enforced policy in which a server uses response headers to say which other origins may read its responses. It controls reading in the browser, not access to the server, and is not authentication.

curl

A command-line tool for making HTTP requests. -i includes the status line and response headers in the output; -H adds a request header. It runs from wherever your shell runs and does not enforce CORS.

DevTools

The browser’s built-in developer tools. The Network panel records the page’s requests and responses while open; the Console shows JavaScript errors and browser policy messages.

DNS

Domain Name System: the service that turns host names into IP addresses. Answers are cached for each record’s time-to-live (TTL), so a change can take time to reach every client.

FastAPI

A Python web framework. You declare path operations—an HTTP method plus a path mapped to a function—and FastAPI returns the function’s result as JSON.

fetch()

The browser’s JavaScript function for HTTP requests. It returns a promise that resolves when a response arrives—even a 404 or 500—and rejects on network failures or blocked requests. It has no built-in timeout option.

Host

The part of a URL that names the machine to contact, such as 127.0.0.1, localhost, or api.example.com. It must be resolved to an address from the caller’s point of view.

HTTP status code

A three-digit number summarising how a server handled a request: 2xx success, 3xx redirection, 4xx a client-side problem such as 404 Not Found, 5xx a server-side failure such as 500. A 200 is not proof the body is correct.

Hypothesis

A proposed explanation that predicts something you have not observed yet. A useful one can be tested—and proved wrong—by a specific observation.

Idempotent

Repeating an operation has the same intended effect as doing it once. HTTP defines GET, HEAD, PUT, DELETE, OPTIONS and TRACE as idempotent; POST is not inherently so. This does not make unlimited retries safe: load and side effects still matter. A non-idempotent operation needs an explicit deduplication/retry contract.

localhost

A host name meaning “this machine or network namespace, from the caller’s point of view.” It usually resolves to 127.0.0.1 and/or ::1. Its meaning changes with the context that resolves it.

Loopback interface

A virtual network interface whose traffic never leaves the machine or namespace that sent it. 127.0.0.1 is the IPv4 loopback address; ::1 is the IPv6 one.

Network namespace

A network context with its own interfaces, routes, ports and loopback. Ordinary isolated containers and Pods differ from the host; host-network or shared-namespace modes are exceptions. Containers within one ordinary Pod share its context.

Origin

The scheme, host and effective port of these HTTP(S) pages, normalized by URL parsing—not the full address-bar string. Localhost and 127.0.0.1 remain different hosts and origins even if both reach the same machine. A path is not part of this tuple.

Port

A number from 0 to 65535 that lets one machine run many network services. A process listens on a port; a connection to a port with no listener is refused.

Preflight request

An automatic OPTIONS request the browser sends before certain cross-origin requests—such as those with a JSON content type or custom headers—to ask the server whether the real request is allowed. Its result can be cached for Access-Control-Max-Age seconds.

response.ok

A boolean on a fetch Response that is true only when the status is in the range 200–299. Code must check it (or the status) before treating a body as success.

Root cause

A causal condition demonstrated within a stated scope. Test alternatives and verify a relevant correction. One surviving hypothesis or one recovery does not prove a unique or complete cause; contributing conditions may remain.

Scheme

The URL prefix, such as http or https, naming the protocol. HTTPS to a plain-HTTP listener can fail; an HTTPS page fetching insecure non-loopback HTTP normally faces mixed-content blocking. Inspect actual browser policy rather than generalizing the local lab.

traceparent

A W3C propagation header. Version 00 fields are version, trace-id, parent-id and trace-flags. Parent-id identifies the caller's operation. Instrumented, retained spans can be joined using context; a header alone does not guarantee a complete trace or causal diagnosis.

uvicorn

An ASGI server commonly used to run FastAPI. It opens the network listener (by default 127.0.0.1:8000), accepts connections, passes requests to the app, and prints access and error logs.

Vite

A frontend build tool and development server. In development it serves source files to the browser (default port 5173). Variables prefixed VITE_ are read at startup or build time and exposed to client code, so they must never hold secrets.

Vary: Origin

A response header telling caches that the response differs depending on the request’s Origin header. Without it, a shared cache can serve one origin’s CORS headers to another.

Mixed content

A secure page loading insecure resources. Browsers block insecure fetches under mixed-content rules, but loopback resources have special potentially-trustworthy treatment. Other restrictions may still apply. Read the actual Console diagnostic; Week 1 does not validate HTTPS deployment.

Path / route

The part of a URL after the host and port, such as /api/status. A server maps method + path to code; a reachable server with no matching route returns 404.

Load balancer / proxy

A layer between client and server that accepts connections and forwards them to one of several backends. It can answer on the backend’s behalf—for example with 502 or 503—so the backend never sees or logs the request.

Mapped model and its limits

A shop directory maps to the page files delivered by Vite; following a separate counter address maps to the browser's API request; a numbered counter and named task map to port and method/path; the reply reaching the customer maps to the rendered API result. Seeing the directory does not prove the clerk is available. A counter number is not permission: this analogy does not model CORS or authentication. Return to the actual Origin and response headers for browser read policy.
