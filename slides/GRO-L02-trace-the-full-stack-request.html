GRO-L02 · Trace the Full-Stack Request

The page renders.
The data card still fails.

The Week 1 app is two programs on two ports: a Vite dev server and a FastAPI process. The browser coordinates the UI and initiates the HTTP request. React can load perfectly while the API is down, because the files that render the screen came from a different server than the one the data depends on.

Where did the request stop, and what evidence identifies that boundary?
Frontend asset loadVite serves HTML / JS / CSS; React renders the root
Browser → API fetchA separate request, to a separate host:port
Response + browser policyStatus, body, and CORS are all independent checks

A React screen loading successfully is not evidence the API is reachable. An API's own /docs page working is not evidence the browser can reach it either — the browser-to-API path has its own requirements.

Key Takeaways

One UI message, many possible boundaries.

  • Two servers, two requests. The HTML/JS load and the API fetch are independent — one succeeding says nothing about the other.
  • Each instrument has a scope. Address bar, Network, Console, curl, server logs, and source files each prove a different slice.
  • Status ≠ correctness. fetch() resolves even on 404/500 — application code must check response.ok.
  • CORS is a read policy, not auth. A request can reach the server while the browser is still blocked from reading the response.
  • Same symptom, different causes. Wrong target, stopped process, and CORS mismatch all look identical from the UI.
  • localhost is relative. Always verify from the exact process that initiates the connection.
